# Продакшен-готовність: що є, чого бракує, що зробити

Аудит усього проєкту, 2026-09-27, оновлено 2026-09-28 (живий фідбек
користувача → розділ 3а, ТРИ КРИТИЧНІ ФІКСИ нижче вже реалізовані; +
новий повний спек вимог від користувача 2026-09-28 — `docs/decisions.md`,
розбивка на чекбокси PLAN.md "Фаза 5"). Відповідає на три питання:
**що реалізовано**, **що пропущено**, **що потрібно доробити, щоб це
можна було називати продакшен-версією** (розгортання на VPS, робота
без щоденного ручного нагляду).

- Поточні живі цифри й деталі кожного кроку — `docs/status.md`.
- Фази й чекбокси — `PLAN.md`.
- Чому кожне рішення таке — `docs/decisions.md`.

Це єдиний документ проєкту, що тримає список "що не готово для
продакшену" — не плодити паралельні чорновики поруч (`docs/draft-todo.md`
злито сюди й видалено 2026-09-28).

**Коротка оцінка.** Інфраструктура (збір даних, оркестрація, БД,
сповіщення) — готова й працює сама. Аналітика — готова частинами.
Продакшеном це ще не є з ТРЬОХ причин:
1. **Прогнозування**, заявлене першим реченням опису проєкту, доведене
   до робочого стану лише на 1 показнику з 15 і нікуди не виходить.
2. **Дані ніде не бекапляться**, при тому що "ніколи не видаляти сирі
   дані" — критичне правило №6 проєкту.
3. **Звітність не доносить те, що вже пораховано** (підтверджено живим
   використанням 2026-09-28, розділ 3а) — скринінг акцій рахується
   щодня й ніколи не потрапляє в Telegram (ще не виправлено), а
   "найбільш підтверджені" історії глобального синтезу насправді часто
   НЕ підтверджені жодним другим джерелом (ще не виправлено). Дедуп
   новин (ранкове й вечірнє сповіщення були однакові) — ✅ виправлено
   того самого дня.

## 3а. Підтверджено живим використанням (2026-09-28) — найвищий пріоритет

На відміну від розділів вище (аудит коду) — це розбір конкретних
симптомів, які користувач побачив у щоденному використанні за кілька
днів роботи, з підтвердженням у коді (файл:функція). Найдешевше й
найважливіше полагодити — тут, не нові фічі.

**1. "Список активів я так і не отримав" — скринінг S&P 500 нікуди не шле.**
`analysis/screening/composite_score.py` рахує Tier A→B→C і пише в
`screening_results` щодня (`screening_composite_score`@5:00), але
жодного reporting-скрипта, який би це надсилав, не існує — з 7
notify-скриптів у `reporting/` жодного для скринінгу. Те саме тепер і
для `crypto_screening/` (LONG/SHORT — PLAN.md, Крок 5, теж не готовий).
→ Потрібен `reporting/screening_notify.py` (+ такий самий для крипто-
скринінгу, коли Крок 5 дійде) і джоба в розкладі одразу після
`screening_composite_score`.

**2. "Ранкові й вечірні новини ідентичні" — ✅ ВИПРАВЛЕНО 2026-09-28.**
`reporting/news_notify.py` (`news_notify_watchlist`@6:30 і 18:30) раніше
завжди читав "останні 5 релевантних за 7 днів" без запису "вже
надіслано" — тепер `WHERE a.notified_at IS NULL` + фільтр за
`confidence` (не "останні N регардлесс якості") + `mark_notified()`
одразу після відправки, той самий захист, що вже був у
`expectations_notify.py`. Заразом той самий фікс застосовано до решти
3 notify-скриптів (`synthesis_notify`/`market_notify`/
`candidates_notify`) — `docs/decisions.md`. Live-підтвердження
(реальний Telegram-чат користувача) ще попереду — код+тести готові.

**3. ✅ ЗНАЧНОЮ МІРОЮ ВИПРАВЛЕНО 2026-09-28/29 — "Аналіз новин нікудишній".**
Стара причина (`top_clusters()` сортував по `source_count`, але
кластеризація майже завжди давала `[1 джерело]`, тож фактично видавав
"найсвіжіші", не "найбільш підтверджені") закрита новою архітектурою:
`consolidate.py` тепер рахує `source_count` МЕХАНІЧНО (сума статей у
змерджених кластерах, об'єднання title-схожості) як головний сигнал
важливості, а LLM-`confidence` лишили лише порогом релевантності — не
мірилом важливості. Окремий LLM-прохід `merge_similar.py` додатково
об'єднує семантичні дублі МІЖ прогонами (переклади/перефразування
того самого факту — text-similarity emпірично підтверджено
ненадійним для цього, docs/decisions.md 2026-09-29). Перекладом і
прив'язкою до активу тепер займається сам `consolidate.py`
(промпт вимагає переклад) — старий пункт про неперекладені заголовки
в `market_notify.py`/`daily_digest.py` (старий пайплайн, `news_analysis`)
лишається відкритим для ТИХ двох скриптів окремо.

**4. ✅ ВИПРАВЛЕНО 2026-09-29 — "Новин за день майже немає".**
Причина встановлена і не одна: (а) `GENERAL_TERMS` не покривав
лексику обвалу ринку (crash/selloff/S&P500/Dow/Nasdaq) — підтверджено
SQL-запитом (0 статей у `raw_news` попри реальний живий обвал), тепер
розбито на `GENERAL_TERMS_MOVEMENT`/`GENERAL_TERMS_EVENTS`, 2 окремі
GDELT-запити (ліміт 150 символів); (б) `fed_rss`/`ecb_rss`/`boj_rss`
публікують рідко — суворе 24г-вікно свіжості губило їх ПОВНІСТЮ
(fed_rss повертав 20 реальних записів, 0 доходило до БД) — виправлено
per-source розширеним вікном (7 днів, лише для цих трьох джерел,
рішення користувача); (в) GDELT 429 на спільному dev-IP — не усунено
(зовнішній ліміт), але пом'якшено: `retries` для `news_collect_*`
джоб підняті з 1 до 3 (P1 №8 нижче).

**5. "Календаря подій з аналізом на тиждень і висновками — не маю".**
Такого звіту не існує в коді взагалі. `monitoring/` зберігає ДАНІ
календаря (`release_log`), але немає reporting-скрипта, який би раз на
тиждень форматував "що виходить цього тижня + чому це важливо" —
`daily_digest.py` показує лише вже готові події за минуле вікно, не
наперед.
→ Новий `reporting/weekly_outlook.py`: читає `pending`-рядки
`release_log` на 7 днів вперед (`refresh_calendar.py` вже їх заводить),
групує за `impact_level`, і — якщо прогнозування (розділ 3, "Головне")
буде доведено — додає власний прогноз як третю точку зору.

## 4. Що потрібно для продакшен-версії

### P0 — без цього називати продакшеном не можна

**1. Автоматичний бекап БД.** Зараз єдина копія всіх зібраних даних —
docker volume `db_data`. `pg_dump` немає ні в `orchestration/jobs.py`,
ні в `scripts/` — лише як ручний рецепт у README, поруч із `docker
compose down -v`, який цей volume знищує. Прямо суперечить критичному
правилу №6 ("ніколи не видаляти сирі зібрані дані") — правило захищає
від DELETE у коді, але не від втрати диска.
→ Джоба `db_backup` (щодня, `pg_dump`, N останніх копій, окремий том
або off-site) + перевірка, що дамп реально відновлюється.

**2. Прогнозування — довести до робочого стану** (розділ 3, "Головне").
Мінімум: backtest усіх 15 показників, відсів тих, де тренд не б'є
naive, вивід прогнозу назовні як третьої точки зору.

**3. Звітність — доносити те, що вже пораховано** (розділ 3а, №1-2, №5).
✅ **Дедуп і фільтр важливості — РЕАЛІЗОВАНО 2026-09-28** (`docs/decisions.md`):
`news_notify.py` більше не шле "останні N регардлесс якості" (фільтр
за `confidence`), і всі 4 залишкові notify-скрипти (`synthesis_notify`/
`market_notify`/`candidates_notify` + вже готовий `expectations_notify`)
тепер мають `notified_at`-дедуп через `reporting/_common.py:mark_notified()`.
**Ще не зроблено:** `screening_notify.py` (список активів ніколи не
надсилається — розділ 3а №1) і `weekly_outlook.py` (розділ 3а №5) —
код ще не написаний, вимоги до них тепер частина ширшого нового спеку
(PLAN.md "Фаза 5" — сесійний розклад звітності, календар подій).

**4. Контроль живості планувальника (heartbeat).** Telegram-алерти про
провал надсилає `runner.py`, тобто сам scheduler. Якщо контейнер
`scheduler` у crash-loop або БД недоступна на старті — не надійде
жодного повідомлення, і система тихо стоїть скільки завгодно довго.
→ Щоденне "я живий" повідомлення, або зовнішній watchdog, або обидва.

**✅ Перший практичний крок — РЕАЛІЗОВАНО 2026-10-02** (живий випадок
користувача: реліз NFP/Unemployment о 15:30 опрацьовано лише о 17:57 —
сам конвеєр check_releases→...→notify_expectations займає ~15 хв,
причина затримки була в непоміченому ~11-год простої контейнера
`scheduler`): `jobs.py:_scheduler_heartbeat` пише `now()` у
`scheduler_heartbeat` (один рядок) кожні 5 хв; `main.py:check_startup_gap`
звіряє його з поточним часом ПРИ СТАРТІ процесу — розрив понад 20 хв
шле один Telegram-алерт (`alerts.py:notify_scheduler_gap`) із тим, на
скільки й коли саме стояв простій. **Межа рішення:** це виявляє простій
лише ПОСТФАКТУМ, при наступному запуску процесу — не зовнішній
watchdog і не alert у реальному часі під час самого crash-loop (якщо
контейнер постійно падає й рестартиться сам, не затримуючись — кожен
рестарт проходить перевірку, тож короткий crash-loop теж зловиться; не
зловиться лише нескінченний crash БЕЗ жодного успішного старту —
для цього все ще потрібен зовнішній watchdog, нижче).

**✅ Суміжне вже РЕАЛІЗОВАНО 2026-09-28 — ретрай окремої джоби:**
`runner.py` тепер повторює провалену джобу (дефолт: 1 повторна спроба,
60с пауза) перш ніж сповістити Telegram — транзієнтний мережевий збій
(найчастіша причина провалу джоб збору даних) більше не означає "чекай
до наступного циклу". Це НЕ замінює heartbeat вище — ретрай рятує від
транзієнтних збоїв ОДНІЄЇ джоби, не від падіння всього процесу
scheduler.

### P1 — реальні ризики, які проявляться в експлуатації

**5. Гонка `check_releases` → `update_forecasts` (+1 хв).**
`check_releases` ходить у FRED/ECB/BOJ/e-Stat по ВСІХ показниках, час
яких настав; легко перевищує хвилину. Якщо він ще працює, коли о +1 хв
стартує `update_forecasts`, той не побачить рядків `'detected'`, а
`compare_expectations` о +5 хв уже переведе їх у `'processed'` — і
прогноз для цього релізу не оновиться ніколи. Тихо, без помилки.
→ Зсунути `update_forecasts` після `compare_expectations` і дати йому
власний прапорець "прогноз оновлено", або окремий статус на споживача.

**6. Реліз "з'їдається" без результату.** `compare_releases.py` ставить
`'processed'` навіть коли порівняння пропущено через нестачу історії —
рядок зникає з вибірки назавжди.

**7. Повторні Telegram-повідомлення поза `news_notify` (розділ 3а, №2
вже підтверджено).** `synthesis_notify`, `market_notify`,
`candidates_notify` мають той самий брак дедупу — теоретичний ризик,
поки не підтверджений так само живо, як `news_notify`.

**8. Ліміти зовнішніх API без обліку.** Twelve Data free tier — 800
запитів/добу; `quotes_universe_refresh` сам з'їдає ~500, плюс
`verify_tradable()` у `discover_candidates` і `watchlist_prices`. GDELT
регулярно віддає 429 (спільний dev-IP, розділ 3а №4) — **пом'якшено
2026-09-29:** `news_collect_watchlist/general/stock` тепер мають
`"retries": 3` (було 1), живо підтверджено (провал о 12:00 успішно
повторився після відновлення GDELT). Підрахунку витрачених запитів чи
алерту при наближенні до ліміту й далі немає.

**9. Немає фіксації версій залежностей.** `requirements.txt` — лише
діапазони. Ребілд образу на VPS через місяць дасть інший набір версій,
ніж перевірений локально. → lock-файл (`pip freeze` у
`requirements.lock`) + білд із нього.

**10. Секрети й доступи на VPS.** `.env` лежить поруч із кодом у

## 5. Чекліст розгортання на VPS

```bash
# 1. Нативний Docker Engine (НЕ Docker Desktop) + git
# 2. Окремий користувач, клон репозиторію, .env
cp .env.example .env && chmod 600 .env    # заповнити ключі
# 3. ufw: дозволити тільки ssh; порт БД уже слухає лише 127.0.0.1
# 4. Перший запуск з чистими даними (~1 год)
bash scripts/bootstrap_1_backfill.sh
bash scripts/bootstrap_2_pipeline.sh
# 5. Перевірити, що планувальник живий і розклад зареєстровано
docker compose logs scheduler | head -40
# 6. ЩЕ НЕ АВТОМАТИЗОВАНО (P0 №1) — бекап:
docker compose exec db pg_dump -U "$DB_USER" "$DB_NAME" > backup_$(date +%F).sql
```

розкладу; `release_log` має рядки `pending`; у Telegram прийшов
щоденний дайджест — **і** (поки P0 №3 не зроблено) варто вручну
перевірити `screening_results`/`crypto_screening_candidates` в БД,
бо самі вони в Telegram не з'являться.
