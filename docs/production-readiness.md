# Продакшен-готовність: що є, чого бракує, що зробити

Аудит усього проєкту, 2026-09-27. Відповідає на три питання:
**що реалізовано**, **що пропущено**, **що потрібно доробити, щоб це
можна було називати продакшен-версією** (розгортання на VPS, робота
без щоденного ручного нагляду).

- Поточні живі цифри й деталі кожного кроку — `docs/status.md`.
- Фази й чекбокси — `PLAN.md`.
- Чому кожне рішення таке — `docs/decisions.md`.

**Коротка оцінка.** Інфраструктура (збір даних, оркестрація, БД,
сповіщення) — готова й працює сама. Аналітика — готова частинами.
Продакшеном це ще не є з двох причин, і обидві НЕ про інфраструктуру:
(1) **прогнозування**, заявлене першим реченням опису проєкту, доведене
до робочого стану лише на 1 показнику з 15 і нікуди не виходить;
(2) **дані ніде не бекапляться**, при тому що "ніколи не видаляти сирі
дані" — критичне правило №6 проєкту.

## 4. Що потрібно для продакшен-версії

### P0 — без цього називати продакшеном не можна

**1. Автоматичний бекап БД.** Зараз єдина копія всіх зібраних даних —
docker volume `db_data`. `pg_dump` немає ні в `orchestration/jobs.py`,
ні в `scripts/` — лише як ручний рецепт у README, поруч із `docker
compose down -v`, який цей volume знищує. Це прямо суперечить
критичному правилу №6 ("ніколи не видаляти сирі зібрані дані —
історичні дані те, на чому тримається якість майбутніх прогнозів"):
правило захищає від DELETE у коді, але не від втрати диска.
→ Джоба `db_backup` (щодня, `pg_dump`, N останніх копій, окремий том
або off-site), + перевірка, що дамп реально відновлюється.

**2. Прогнозування — довести до робочого стану** (розділ 3 вище,
PLAN.md Фаза 2). Мінімум: backtest усіх 15 показників, відсів тих, де
тренд не б'є naive, і вивід прогнозу назовні як третьої точки зору
поруч із фактом і ринковим очікуванням.

**3. Контроль живості планувальника (heartbeat).** Telegram-алерти про
провал надсилає `runner.py`, тобто сам scheduler. Якщо контейнер
`scheduler` у crash-loop (напр. синтаксична помилка в `schedule.py`
після правки) або БД недоступна на старті — не надійде **жодного**
повідомлення, і система тихо стоїть скільки завгодно довго. Зараз це
помітно тільки заглянувши в `docker compose logs`.
→ Щоденне "я живий" повідомлення, або зовнішній watchdog
(healthcheck-пінг), або обидва.

### P1 — реальні ризики, які проявляться в експлуатації

**4. Гонка `check_releases` → `update_forecasts` (+1 хв).**
`check_releases` ходить у FRED/ECB/BOJ/e-Stat по ВСІХ показниках, час
яких настав; легко перевищує хвилину. Якщо він ще працює, коли о +1 хв
стартує `update_forecasts`, той не побачить рядків `'detected'`, а
`compare_expectations` о +5 хв уже переведе їх у `'processed'` — і
прогноз для цього релізу не оновиться **ніколи** (наступний цикл їх не
побачить). Тихо, без помилки.
→ Або зсунути `update_forecasts` після `compare_expectations` і дати
йому власний прапорець "прогноз оновлено" замість читання `'detected'`,
або ввести окремий статус на кожного споживача.

**5. Реліз "з'їдається" без результату.** `compare_releases.py` ставить
`'processed'` навіть коли порівняння пропущено через нестачу історії
(`len(observations) < required`) — рядок зникає з вибірки назавжди, і
сюрприз для цього релізу не порахується, навіть коли історія набереться
через день.

**6. Повторні Telegram-повідомлення.** Захист "вже надіслано"
(`notified_at`) є лише в `expectations_notify.py`. `news_notify`,
`synthesis_notify`, `market_notify`, `candidates_notify` завжди шлють
"останній стан": якщо за добу нових подій менше за `--limit`, у чат
щодня йде те саме. Для щоденної роботи це поступово перетворює канал у
шум, який перестають читати — тобто знецінює всі сповіщення разом.

**7. Ліміти зовнішніх API без обліку.** Twelve Data free tier — 800
запитів/добу; `quotes_universe_refresh` сам з'їдає ~500, плюс
`verify_tradable()` у `discover_candidates` і `watchlist_prices`. GDELT
уже регулярно віддає 429. Немає ні підрахунку витрачених запитів, ні
алерту при наближенні до ліміту — перші симптоми будуть у вигляді
випадково неповних даних.

**8. Немає фіксації версій залежностей.** `requirements.txt` — лише
діапазони (`requests>=2.31,<3`). Ребілд образу на VPS через місяць дасть
інший набір версій, ніж перевірений локально. → lock-файл
(`pip freeze` у `requirements.lock`) + білд із нього.

**9. Секрети й доступи на VPS.** `.env` лежить поруч із кодом у
plaintext (DB_PASSWORD, 4 API-ключі, Telegram-токен). Мінімум:
`chmod 600 .env`, окремий користувач для проєкту, `ufw` (порт БД уже
прив'язаний до 127.0.0.1 — `docs/decisions.md` 2026-09-27).

### P2 — бажано, не блокує

10. `healthcheck` для сервісу `scheduler` у `docker-compose.yml` (зараз
    лише для `db`) — щоб `docker compose ps` показував реальний стан.
11. Деградація при збоях LLM: 429/5xx зараз = пропуск до наступного
    циклу; для щоденних синтезів це дірка за цілу добу без ретраю.
12. Ліміти ресурсів контейнерів (`deploy.resources`) — щоб один
    розрослий процес не поклав увесь VPS.
13. `docs/decisions.md` — 1892 рядки без змісту; варто додати індекс або
    архівувати записи, старші за поточну фазу (архів уже є —
    `docs/archive/`).

## 5. Чекліст розгортання на VPS

```bash
# 1. Нативний Docker Engine (НЕ Docker Desktop) + git
# 2. Окремий користувач, клон репозиторію, .env
cp .env.example .env && chmod 600 .env    # заповнити ключі
# 3. ufw: дозволити тільки ssh; порт БД уже слухає лише 127.0.0.1
# 4. Перший запуск з чистими даними (~1 год)
bash scripts/bootstrap_1_backfill.sh
bash scripts/bootstrap_2_pipeline.sh
# 5. Перевірити, що планувальник живий і розклад зареєстровано
docker compose logs scheduler | head -40
# 6. ЩЕ НЕ АВТОМАТИЗОВАНО (P0 №1) — бекап:
docker compose exec db pg_dump -U "$DB_USER" "$DB_NAME" > backup_$(date +%F).sql
```

Перевірка через добу після старту: `logs/` містить файли всіх джоб
розкладу; `release_log` має рядки `pending`; у Telegram прийшов
щоденний дайджест.
