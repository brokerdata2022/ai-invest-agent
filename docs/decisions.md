# Журнал рішень (ADR-лайт)

Формат кожного запису: дата, що вирішили, чому, які альтернативи відкинули.
Мета — щоб через 3 місяці (або нова сесія Claude) не довелось заново

### 2026-08-29: raw_observations зберігає тільки сирі значення, не % зміни
**Рішення:** data-ingestion/ ніколи не рахує й не зберігає похідні
величини (MoM/YoY % зміна, тренди, порівняння факт/консенсус) —
тільки сире значення показника, яке віддає джерело. Розрахунки
живуть у analysis/ і рахуються з сирих значень на льоту або в
окремих похідних таблицях (деталі — коли дійдемо до Фази 2).
**Чому:** з сирого індексу (напр. CPI = 314.121) можна порахувати
будь-яку зміну (MoM, YoY, QoQ, зміна від попередньої ревізії) — не
треба наперед вирішувати, яка саме знадобиться. Якщо зберігати
одразу готовий %, втрачаємо гнучкість і, що важливіше, ламаємо
коректну обробку ревізій (коли джерело переглядає минуле значення
заднім числом — % зміна "з коробки" стає неоднозначною: від якої
версії минулого значення її рахували?).
**Відкинута альтернатива:** тягнути з FRED вже готові % через
параметр `units=pch/pc1` як окремі metric_id. Відкинуто на цьому
етапі — дублює дані, прив'язує нас до методології розрахунку FRED
замість власної, і суперечить принципу "джерело даних не інтерпретує".
Можна повернутись до цього як до додаткової звірки в Фазі 2.
Повний список показників для Фази 1+ — docs/metrics-catalog.md.

### 2026-08-27: Стек — Python + PostgreSQL/TimescaleDB
**Рішення:** Python як мова бекенду; PostgreSQL з розширенням
TimescaleDB як єдина база даних (замість окремих time-series + реляційної
СУБД).
**Чому:** один інструмент для обох типів даних (ціни/показники як
часові ряди, метадані/звіти як реляційні дані) — менше операційної
складності, ніж підтримка двох окремих СУБД. Обидва компоненти
безкоштовні й з відкритим кодом.

### 2026-08-27: Джерела даних — пріоритет безкоштовних першоджерел
**Рішення:** повний список у data-ingestion/CLAUDE.md. Ключові вибори:
FRED/ECB SDW для макро, SEC EDGAR для звітів компаній, yfinance для
цін (акції/форекс/товари), CoinGecko + Binance public API для крипти,
GDELT + офіційні RSS для новин.
**Чому:** максимальне покриття безкоштовно, з пріоритетом на офіційні
першоджерела там, де вони існують (FRED, SEC EDGAR, ECB, Binance).
Там, де офіційного безкоштовного API немає (ціни акцій/форекс/товарів
у реальному часі) — свідомо йдемо на компроміс через yfinance, з
явним застереженням про неофіційність і вимогою ізолювати це за
адаптером.
**Відкинуті альтернативи:** Alpha Vantage як основне джерело цін
акцій — відкинуто через занадто обмежений безкоштовний рівень (25
запитів/день), непридатний навіть для помірного покриття ринку.

### 2026-08-27: Календар релізів з рівнем впливу — власна розмітка
**Рішення:** дати релізів беремо з офіційних графіків публікацій
(BLS/BEA/Fed/ECB), а рівень впливу (High/Medium/Low) підтримуємо як
власний статичний список типів релізів, а не з зовнішнього API.
**Чому:** офіційного безкоштовного API з готовою розміткою впливу не
існує — найпоширеніші джерела такої розмітки (напр. ForexFactory)
неофіційні. Розмітка "що є high-impact" — загальновідома і рідко
змінюється (NFP, CPI, FOMC, GDP, PCE), тому підтримувати її вручну —
прийнятний компроміс.

### 2026-08-29: Виправлення — partition column для hypertable — observed_at, не fetched_at
**Рішення:** raw_observations партиціонується (TimescaleDB hypertable) по
`observed_at`, а не по `fetched_at`, як було зроблено спочатку.
**Чому:** перша спроба (partition по fetched_at) впала з реальною помилкою
під час запуску: `create_hypertable()` вимагає, щоб УСІ unique-обмеження
таблиці (не тільки PRIMARY KEY) включали колонку партиціювання. Наш
`UNIQUE (source, metric_id, observed_at, revision)` не містив fetched_at,
і hypertable не створювався — весь init-скрипт після цього кроку
переривався, включно з `INSERT INTO sources`, що спричиняло
ForeignKeyViolation при першому запуску run_collect.py. observed_at і
так частина цього UNIQUE-обмеження, тож партиціювання по ньому
розв'язує проблему без штучного розширення ключа. Додатковий бонус:
типові запити analysis/ читають "дані за період X" (observed_at), не
"коли ми дізнались" (fetched_at) — тож це й ефективніше.
**Наслідок для існуючих локальних БД:** якщо volume вже піднімався зі
старою схемою (і впав на цьому кроці), треба `docker compose down -v`
і підняти заново — таблиця не встигла отримати жодних валідних даних
(усі insert'и падали на FK через незаповнену sources), тож втрати
історії немає.

### 2026-08-29: Revision обчислює шар збереження, не адаптер
**Рішення:** адаптери (напр. FredAdapter) завжди повертають
NormalizedRecord з `revision=None`. Фактичний номер ревізії визначає
`common/db.py:decide_revision()` під час запису — порівнянням нового
значення з останнім уже збереженим для того самого
(source, metric_id, observed_at).
**Чому:** data-ingestion/CLAUDE.md вимагає, щоб адаптер повертав
`revision` як частину нормалізованого запису, але визначити ревізію
можна лише знаючи історію — а адаптер за архітектурою (docs/architecture.md)
не повинен звертатись до сховища. Винесення рішення "яка це ревізія"
в окрему чисту функцію (без SQL) дозволяє покрити логіку тестами без
реальної БД і лишає адаптер простим: він не знає нічого, крім самого зовнішнього API.
**Відкинуті альтернативи:** давати адаптеру доступ до БД для
самостійного визначення ревізії — відкинуто, бо порушує розділення
"адаптер тільки збирає" і ускладнює тестування адаптерів (довелось би
мокати БД в кожному тесті адаптера, а не лише в тестах db.py).

## Приклад запису (видалити, коли з'явиться перше реальне рішення)
### 2026-08-24: Формат сховища сирих даних
**Рішення:** append-only таблиці, без update/delete для фактичних даних.
**Чому:** потрібна можливість порівнювати "що знали тоді" з реальністю
пізніше; видалення/перезапис ламає цю можливість назавжди.
**Відкинуті альтернативи:** тримати тільки останнє значення кожного
показника (простіше, але втрачає історію ревізій даних, яка сама по собі
є сигналом).
