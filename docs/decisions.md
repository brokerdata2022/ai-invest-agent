**Чому:** один інструмент для часових рядів і реляційних даних —
менше операційної складності; обидва компоненти безкоштовні.

### 2026-08-27: Джерела даних — пріоритет безкоштовних першоджерел
**Рішення:** FRED/ECB SDW (макро), SEC EDGAR (звіти компаній),

**Чому:** максимальне покриття безкоштовно, з пріоритетом офіційних
першоджерел там, де вони існують.
**Відкинуто:** Alpha Vantage як основне джерело цін акцій — 25

### 2026-08-27: Календар релізів з рівнем впливу — власна розмітка
**Рішення:** дати релізів — з офіційних графіків (BLS/BEA/Fed/ECB),
рівень впливу (High/Medium/Low) — власний статичний список.
**Чому:** офіційного безкоштовного API з готовою розміткою впливу не

### 2026-08-29: Новий адаптер = новий рядок у sources + перевірка кожного series key живим запитом
**Рішення:** при додаванні адаптера нового джерела обов'язково:
1) рядок у seed `INSERT INTO sources` (db/schema.sql); 2) кожен
series key перевірити живим запитом до live-тесту користувача.
**Чому:** обидва ризики виявились реальними на ecb_adapter.py —
відсутність джерела в `sources` ловиться тільки на реальному insert
(`ForeignKeyViolation`), а series key з непрямих джерел (старі
довідники, статті) виявився застарілим (404).
**Відкинуто:** довіряти юніт-тестам на фікстурах як доказу готовності
до live-тесту — вони перевіряють тільки `normalize()`, не існування
джерела в БД чи актуальність зовнішнього API.

### 2026-08-29: raw_observations зберігає тільки сирі значення, не % зміни
**Рішення:** data-ingestion/ ніколи не рахує похідні величини (MoM/YoY
% зміна) — тільки сире значення від джерела. Розрахунки — в analysis/.
**Чому:** з сирого індексу можна порахувати будь-яку зміну на вимогу;
зберігання готового % ламає коректну обробку ревізій (від якої версії
минулого значення рахувати %?).
**Відкинуто:** тягнути з FRED готові `units=pch/pc1` як окремі
metric_id — дублює дані й прив'язує до методології FRED.

### 2026-08-29: Виправлення — partition column для hypertable — observed_at, не fetched_at
**Рішення:** raw_observations партиціонується по `observed_at`, не
`fetched_at` (як було спочатку).
**Чому:** `create_hypertable()` вимагає, щоб УСІ unique-обмеження
включали колонку партиціювання; наш `UNIQUE(source, metric_id,
observed_at, revision)` не містив `fetched_at` — hypertable не
створювався, init-скрипт падав з `ForeignKeyViolation`. `observed_at`
уже в цьому UNIQUE, і це природніша вісь для типових запитів analysis/
("дані за період X", не "коли дізнались").

### 2026-08-29: Revision обчислює шар збереження, не адаптер
**Рішення:** адаптери завжди повертають `revision=None`; фактичний
номер визначає `common/db.py:decide_revision()` під час запису —
порівнянням з останнім збереженим значенням.
**Чому:** визначити ревізію можна лише знаючи історію, а адаптер не
повинен звертатись до сховища (docs/architecture.md); чиста функція
без SQL дозволяє тестувати логіку без реальної БД.
**Відкинуто:** давати адаптеру доступ до БД для самовизначення ревізії
— порушує розділення "адаптер тільки збирає", ускладнює тестування.

### 2026-08-30: "Живий запит повернув 200 OK" ≠ "series key досі актуальний"
**Рішення:** якщо отримане значення застаріле більш ніж на один
звітний період — перевіряти, чи датасет не замінено/закрито джерелом,

джерела в ключі серії. Запит до старого flowRef не падав помилкою —
просто не отримував нових спостережень. Виправлено:
`eurozone_hicp` → `HICP.M.U2.N.000000.4D0.ANR`.

легітимна ревізія. Розглянути поріг-попередження на рівні collect_all.py

1. **Stooq** (перший вибір) — без ключа й реєстрації, здавався
   найпростішим.
2. **→ Alpaca Markets** — закривав і котирування, і universe одним
   джерелом; відкинуто: сайт/API географічно недоступні з України
   (недокументований гео-блок), а сам факт вимагав реєстрації
   реального акаунту.
3. **→ Stooq знову** + SEC `company_tickers_exchange.json` для universe
   (без акаунтів). Живий тест: `delimiter=";"` (польський регіональний
   формат CSV), не `,` — виявлено тільки через реальний файл від
   користувача, не через пошук у вебі.
4. **→ Twelve Data (фінально)** — Stooq відкинуто остаточно: JS-based
   бот-захист (Cloudflare-подібний) віддає HTML-сторінку верифікації
   замість CSV при запиті без browser-like User-Agent; `requests` не
   може це пройти без headless-браузера. Twelve Data підтверджено
   живим запитом користувача (email+пароль, без капчі, ключ одразу в
   кабінеті; ~8 запитів/хв, 800/добу; помилки — HTTP 200 з
   `status:"error"` в тілі, не HTTP-кодом).
**Урок:** для будь-якого джерела "без реєстрації/без ключа" — попросити
живу перевірку одним запитом ДО написання адаптера; вебпошук про
поведінку зовнішнього API не заміняє реального запиту чи файлу
(тричі підряд один живий тест дав більше сигналу, ніж година пошуку).
**Universe:** S&P 500 (не весь `company_tickers_exchange.json`, кілька
тисяч тикерів) — вже попередньо якісний ліквідний пул, і суттєво
менше запитів за прогін скринера.

### 2026-09-25: Виправлено N+1 SQL-запити в analysis/screening/ — batch-запити замість запиту на кожен тикер
**Що сталось:** живий прогін tier_a.py зайняв ~9.5 хв на 491 тикер;
tier_b.py — ще довше (перевіряє 6 SEC EDGAR концептів на тикер).
Причина — не розмір результату, а те, що `v_current_values`/
`v_observations_latest_revision` — DISTINCT ON-views над TimescaleDB
hypertable з дрібним (дефолтним) chunk_time_interval: для тикерів з
десятиліттями історії (Twelve Data) це тисячі чанків, і кожен окремий
запит без обмеження по `observed_at` змушений перевірити кожен чанк —
фіксовані накладні витрати ~100-150мс НЕЗАЛЕЖНО від розміру
результату. tier_a.py робив 3 запити/тикер, tier_b.py — 6/тикер:
491-411 тикерів × (3-6) запитів = 1500-2500+ послідовних запитів.
**Рішення:** новий спільний модуль `analysis/screening/_batch_db.py`
— `batch_latest_values()`/`batch_series()` беруть СПИСОК metric_id і
роблять ОДИН запит (`WHERE metric_id = ANY(список)`) замість запиту
на кожен. Накладні витрати сканування чанків платяться один раз для
всього списку тикерів, а не N разів. tier_a.py: 3×N → 4 запити
загалом. tier_b.py: 6×N → 6 запитів загалом. tier_c.py: 2×N → 2
запити загалом.
**Побічний фікс (той самий корінь, редундантний перерахунок):**
`tier_b.py`/`tier_c.py`/`composite_score.py` за замовчуванням (без
явно переданих `tier_a_results`) кожен викликав `run_tier_a()` ще раз
із нуля, навіть якщо виклик уже мав готовий результат вище по
ланцюжку — повний прогін `composite_score.py` рахував Tier A ДВІЧІ.
Виправлено: `tier_a_results`/список тикерів тепер прокидається вниз
по ланцюжку (`run_tier_c()`→`run_tier_b(tier_a_tickers=...)`,
`run_composite_score()`→те саме).
**Чисті функції не змінились:** `passes_tier_a/b/c`, `yoy_growth`,
`ttm_sum`, `all_positive_last_n` — без змін, ті самі пороги, той самий
результат. Новий тестований пурум-хелпер:
`avg_dollar_volume_from_series()` (заміняє SQL JOIN...AVG() з
попередньої версії _avg_dollar_volume()) — 4 нових тести в
test_tier_a.py.
**Не зроблено (окрема, більша задача):** сам chunk_time_interval
hypertable не змінено (дефолтний, дуже дрібний для цього типу даних)
— це вимагало б міграції існуючих чанків, ризикованіше й не потрібне
після фіксу N+1 (batch-запити роблять цю накладну вартість
одноразовою на весь прогін, а не помножену на к-сть тикерів).

### 2026-09-25: MIN_QUERY_LEN — спростовано як причина; реальна проблема — слово "Uber"
**Що сталось:** наступний живий прогін (після мерджу "хвоста", вище)
дав групу 2/2 — `("Huntington Ingalls Industries" OR ... OR "Uber" OR
"Wabtec")`, **175 символів** (вище і MIN_QUERY_LEN=70, і підтвердженого
робочого 117-150) — GDELT ЗНОВУ відхилив тим самим `"The specified
phrase is too short."`. Це прямо спростовує гіпотезу "довжина query"
— 175-символьний query не може бути "занадто коротким" за жодним
розумним визначенням. Єдине спільне між обома збоями (41 і 175
символів) — термін `"Uber"`. Інші короткі однослівні терміни в тих
самих групах ("Emcor" 5 літер, "Wabtec" 6, "Casey's") — жодного разу
не викликали цю помилку.
**Урок (за прямою вимогою користувача "не змінюй код на вгад"):**
перша гіпотеза (MIN_QUERY_LEN) була побудована на ОДНОМУ, сплутаному
прикладі — єдиний короткий query, який на той момент тестувався,
випадково містив і "Uber". Другий живий прогін з контрольованою
змінною (довжина зросла до 175, "Uber" лишився) ізолював справжню
причину. `MIN_QUERY_LEN`/`batch_ticker_names()` merge-крок НЕ
видалено (шкоди не завдає, залишається як захисна евристика "про
всяк випадок"), але коментарі в коді відверто позначають його як
непідтверджений, щоб наступна сесія не сприйняла його як факт.
**Рішення:** `STOCK_NAME_OVERRIDES` — курований словник (той самий
підхід, що й `WATCHLIST_TERMS`/FRED `METRICS`) — для тикера UBER
термін замінюється на повну назву `"Uber Technologies"`. GDELT сам
документує відхилення "дуже коротких АБО дуже загальновживаних" слів
навіть у лапках — "uber" загальновживане англійське слово (підсилювач),
на відміну від специфічних "Emcor"/"Wabtec". Точний критерій
"загальновживаності" GDELT не описує, тому фіксуємо підтверджений
конкретний випадок явно, а не намагаємось вивести загальне правило
з одного прикладу.
**Не перевірено (чесно позначено):** чи є в S&P 500 universe інші
тикери з такою самою проблемою (короткі загальновживані англійські
слова як офіційна назва) — `STOCK_NAME_OVERRIDES` розширюється по
факту виявлення, не проактивним аудитом усіх 500 назв.
**Live-підтвердження фіксу (2026-09-25):** повторний прогін з
`"Uber Technologies"` замість `"Uber"` (query групи 2 — 188 символів,

на вичерпаному retry-бюджеті `429` (спільний dev-IP під важким

### 2026-09-26: news/ — RSS-адаптер (Fed + ECB), останній шматок news/ з початкового плану

### 2026-09-26: rss_adapter.py — .content (байти), не .text — UTF-8 BOM у Fed
**Що сталось:** перший живий прогін — ECB спрацював (15 записів), Fed
впав з "невалідний XML". Діагностика (`response.content[:200]`) —
Fed віддає тіло з UTF-8 BOM (`\xef\xbb\xbf`), але HTTP-заголовок
`Content-Type: text/xml` без `charset`; `requests.Response.text` у
цьому випадку вгадує `ISO-8859-1` (RFC-дефолт для text/* без
charset), BOM перетворюється на 3 сміттєвих символи `ï»¿` ПЕРЕД
`<?xml version=...`, і `ElementTree.fromstring()` відмовляється це
парсити (XML-декларація має бути найпершою).
**Рішення:** `fetch()` повертає `response.content` (сирі байти), не
`response.text` — `ElementTree` сам коректно визначає кодування й BOM
з байтів, без залежності від вгадування `requests`.
**Тест-регресія:** `test_normalize_handles_utf8_bom_bytes` — байти з
BOM-префіксом, той самий клас збою, що й реальний.
**Live-підтвердження фіксу (2026-09-26):** повторний запуск —
`fed_rss` 20 записів (успішно, фікс спрацював), `ecb_rss` 0 нових
(коректний дедуп — ті самі 15 записів, що й до фіксу). DeepSeek
(`run_news_analysis.py --stream geopolitical`) обробив усі 35 нових
RSS-статей без помилок — рішення з монетарної політики (FOMC,
central bank speeches) позначені релевантними, рутинні enforcement-дії
й банківські дозволи — ні, що збігається з очікуваним сигналом.

### 2026-09-26: news/ — фільтр свіжості (GDELT timespan + news_notify.py по published_at)
**Що сталось:** користувач переглянув кілька проаналізованих статей і
знайшов серед них липневу публікацію про рішення по ставці, яке вже
було прийняте у вересні — застаріла, а не актуальна інформація для
мети "розуміти поточний напрямок ринку" (docs/decisions.md, 2026-09-25
"news/ — обсяг..."). Корінь — два окремі пробіли:
1. `GdeltAdapter.fetch()` не обмежував query за часом (`maxrecords=75,
   sort=datedesc`, без `timespan`) — для вузьких query GDELT сягав
   місяцями назад, щоб набрати maxrecords збігів.
2. `reporting/news_notify.py:fetch_recent_relevant()` сортував за
   `a.created_at` (коли МИ проаналізували), не `n.published_at` (коли
   стаття ВИЙШЛА) — стаття, що пролежала в `raw_news` тижнями (append-
   only, rule 6, ніколи не видаляється) і проаналізована пізніше,
   виглядала б як "остання новина" в Telegram-дайджесті.
**Рішення:**
1. `GdeltAdapter.fetch(timespan="3d")` — новий параметр (GDELT DOC API
   підтримує `TIMESPAN`, підтверджено офіційним блогом
   `blog.gdeltproject.org/gdelt-doc-2-0-api-debuts`), дефолт 3 дні;
   `--timespan` прокинуто в `run_collect_news.py`/`collect_stock_news.py`.
2. `fetch_recent_relevant()` — `ORDER BY n.published_at DESC` (не
   `a.created_at`) + `WHERE n.published_at >= now() - max_age_days`
   (дефолт 7 днів, `--max-age-days` в CLI). Релевантна, але
   місяцями стара стаття тепер НЕ потрапить у сповіщення, навіть
   якщо проаналізована щойно.
**Чому не видаляємо старі рядки з raw_news/news_analysis:** rule 6
(CLAUDE.md) — ніколи не видаляти сирі зібрані дані. Старі записи
лишаються (аудит/історія), фільтр свіжості — тільки на рівні читання
(reporting/), не на рівні зберігання.

### 2026-09-26: relevance_filter.py — звужено критерій релевантності + опис статті в промпт
**Що сталось:** користувач переглянув живі результати аналізу й
оцінив забагато статей як "релевантних" без реального сигналу —
корінь: (1) `build_prompt()` давав DeepSeek ЛИШЕ заголовок (GDELT не
дає тексту статті взагалі; RSS дає `description`, але `fetch_unanalyzed()`
навіть не вибирав `raw_payload` з БД, і `build_prompt()` його не
використовував) — DeepSeek вгадував релевантність із заголовка, а
заголовки системно звучать "по темі", не несучи конкретного факту;
(2) `SYSTEM_PROMPT` не мав явного, перевіюваного критерію "що таке
реальна інформація" — тільки загальне "чи може вплинути на ціну".
**Рішення:**
1. `_db.py:fetch_unanalyzed()` — додано `n.raw_payload` у SELECT.
2. `relevance_filter.py:_extract_description()` — дістає `description`
   з `raw_payload`, якщо є (RSS-фіди, не всі); `build_prompt()` додає
   рядок "Опис: ..." коли є контент понад заголовок.
3. `SYSTEM_PROMPT` переписано з явним критерієм `is_relevant=true`
   лише для трьох конкретних категорій (економічний показник з
   цифрами/трендом; геополітична подія з прямим ринковим наслідком;
   конкретний вплив на ціну/тренд активу) і явним списком, що НЕ
   рахується (рутинні регуляторні дозволи, огляди без нових фактів,
   колонки думок, локальні новини без міжнародного виміру, PR без
   фінансової суті) — з правилом "сумніваєшся — false, не true".
**Не ретроактивно:** старі рядки `news_analysis` (проаналізовані до
цього фіксу) НЕ перераховуються — `fetch_unanalyzed()` бере тільки
статті БЕЗ рядка в `news_analysis`, а видаляти/переписувати старі
заборонено rule 6. Новий, строгіший критерій діє тільки на статті,
проаналізовані ПІСЛЯ цього фіксу.

### 2026-09-26: одноразовий виняток з rule 6 — видалено news/-дані, зібрані до фіксів якості
**Рішення користувача (явно, після того як я підняв конфлікт з rule
6):** `TRUNCATE raw_news, news_analysis, llm_call_log` — повне
очищення. Причина, названа користувачем: ці дані зібрані/проаналізовані
ДО фіксів свіжості (`timespan`) і критерію релевантності (вище) —
вони не "валідна історія, що застаріла", а результат ЗАВІДОМО
дефектного процесу (без обмеження давності, без опису статті в
промпті, розмитий критерій релевантності) — тримати їх означає
плутати майбутній аналіз даними, зібраними неправильним методом.
**Чому це НЕ скасовує rule 6 загалом:** rule 6 захищає ВАЛІДНІ сирі
дані (macro observations тощо) від видалення через "джерело
змінилось/зникло" — тут інша ситуація: сам МЕТОД збору/аналізу був
дефектний, не джерело. Це одноразовий виняток для конкретного
випадку, не нова стандартна практика — news/, зібраний ПІСЛЯ цього
очищення (з фіксами), і далі підпадає під звичайне rule 6 (не
видаляти).

### 2026-09-27: оркестрація — APScheduler, не cron/Celery/Prefect/Airflow
**Питання:** блокер №1 (docs/status.md) — хто автоматично запускає
`check_releases.py`/`refresh_calendar.py`/збір новин/скринінг тощо.
**Рішення:** `APScheduler` (`BlockingScheduler`) у власному
docker-compose сервісі `scheduler` (`restart: unless-stopped`), новий
шар `orchestration/`. Голий cron у контейнері не бачить `.env` без
окремого entrypoint-хака й губить логи без syslog-налаштувань;
Celery потребує брокер (Redis/RabbitMQ), Prefect/Airflow — окремий
сервер/БД метаданих — усе це зайве для ~15 незалежних періодичних джоб
без черг і DAG-залежностей (Tier A→B→C вже ланцюжок в одній Python-
функції `composite_score.py`, не окремі задачі). APScheduler — один
pip-пакет, той самий образ/Python, розклад — звичайний код.
**Часовий пояс:** Europe/Kyiv (за замовчуванням, `SCHEDULER_TIMEZONE`
в `.env` перекриває) — переходи літній/зимовий автоматично через
`zoneinfo`, повне геолокаційне автовизначення не має сенсу для
headless-контейнера.
**Розклад в окремому файлі:** `orchestration/schedule.py` — щоб міняти
періодичність без торкання коду джоб (`jobs.py`), користувач сам
редагує один Python-словник (назва → коли + чому), без нового формату/
залежності (YAML/TOML/INI розглядались і відкинуті — зайвий парсер
заради того, що звичайний `.py` і так уміє).
**Провал джоби → Telegram-алерт** (лог + причина, дедуп
`send_telegram_message` в `reporting/telegram_client.py` — раніше
дублювалась у telegram_notify.py/news_notify.py); успіх — тільки
лог-файл, без шуму.
**Продакшен переїде на VPS пізніше** — це звичайний docker-compose
сервіс, тому `docker compose up -d` на VPS піднімає й scheduler без
змін коду.

### 2026-09-27: дублікати в news_synthesis/market_synthesis/candidate_assets — UPSERT "один результат на день"
**Проблема, виявлена першим живим прогоном `daily_digest.py`:** 16
повідомлень дайджесту, з них лише 5 унікальних — `news_synthesis` мав
15 рядків за добу для лише 4 активів (WAB/xauusd/wti_crude/brent_crude),
бо кожен ручний тестовий запуск `synthesize.py` цієї сесії додавав
новий рядок без жодної перевірки, чи вже є результат за сьогодні.
**Питання користувача перед фіксом:** чи "один результат на актив/день"
не згубить кілька РІЗНИХ новин про той самий актив в один день?
**Відповідь, що зняла занепокоєння:** ні — `synthesize.py` і так не
пише "одну новину" в рядок: кожен прогін перечитує ВСІ релевантні
новини за `--max-age-days` (не тільки нові з минулого прогону) і дає
ОДИН зведений LLM-висновок з урахуванням усіх історій одразу
(`source_refs`/`signal.summaries`). Пізніший прогін того самого дня —
не окрема подія, а повніша версія того самого зведення (бачить усе,
що бачив попередній, плюс нове). UPSERT не губить інформації, лише
не дублює застарілу проміжну версію. Користувач підтвердив: лишити
цей підхід.
**Рішення:** `UNIQUE INDEX` на (asset_id, день) для `news_synthesis`,
на (день) для `market_synthesis`, на (ticker, день) для
`candidate_assets` + `ON CONFLICT ... DO UPDATE` у відповідних
`save_*()` (`analysis/news_analysis/_db.py`) замість чистого INSERT.
**Технічний нюанс:** `created_at::date` у виразі індексу Postgres
відхиляє (`functions in index expression must be marked IMMUTABLE`) —
каст timestamptz→date залежить від часового поясу СЕСІЇ, тому не
IMMUTABLE. Виправлено на `(created_at AT TIME ZONE 'UTC')::date` —
явно зафіксований пояс робить вираз детермінованим.
**Живо підтверджено:** очищено 11 старих дублікатів (SQL-скрипт,
залишено найновіший на актив/день), схема застосована, повторний
`daily_digest.py` дав рівно стільки повідомлень, скільки унікальних
подій.

### 2026-09-27: базовий механізм прогнозування — трендові моделі, один показник наскрізно
**Що:** `analysis/forecasting/` — перша реалізація незавершеного пункту
PLAN.md Фази 2 ("почати з простого — трендові моделі — перш ніж
ускладнювати"). Свідомо той самий підхід, що Фаза 0 ("Один-єдиний
адаптер даних — наскрізно, від збору до збереження"): ОДИН показник
(`cpi`) повністю наскрізно (модель → backtest → збереження), а не
одразу всі 15 показників календаря — розширення на решту тривіальне
(параметр `--metric`), але спершу треба довести, що механізм узагалі
має сенс.
**Метод:** звичайна лінійна регресія (МНК) значення від порядкового
номера точки, екстраполяція на 1 крок уперед (`trend.py:
linear_trend_forecast`) — те саме "трендова модель", що прямо назване
в PLAN.md. Той самий файл — `naive_forecast` (останнє значення без
змін), потрібен як базова лінія: analysis/CLAUDE.md вимагає
backtestability саме для того, щоб знати, чи модель взагалі краща за
"нічого не робити".
**Backtest, не інтуїція:** `backtest.py` проходить всю історію
показника, на кожній точці рахує прогноз ЛИШЕ з попередніх точок
(honest out-of-sample, не підглядає майбутнє), порівнює MAE трендової
моделі з MAE naive. Якщо тренд не б'є naive — це сигнал, що для цього
показника лінійний тренд не годиться, а не привід одразу ускладнювати
модель.
**Спрощення (той самий стиль чесності, що yoy_pct/срібло-проксі):**
індекс точки (0,1,2,...), не фактична дата — припускає регулярний
місячний інтервал між спостереженнями CPI, не перевіряє пропуски.
**Свідомо НЕ зроблено цієї сесії:** інтеграція в orchestration/

взагалі варта показу користувачу; інші 14 показників календаря;
складніші моделі (ARIMA/сезонність) — навмисно відкладено, поки
найпростіша версія не доведе або не спростує свою цінність.
**Зберігання:** нова таблиця `metric_forecasts` (один рядок на

даних оновлює рядок, не дублює) — для майбутнього аудиту, коли

здоровій зоні (~50-75, не перегрітий) + funding rate НЕ аномально
високий позитивний (перегрітий/дорогий лонг — ризик squeeze проти
власної позиції).

**SHORT:** сильний памп (ціна) + OI ПОЧИНАЄ ПАДАТИ після пампу
(леверидж-лонги закриваються — класична ознака виснаження) + сплеск
обсягу (підтверджує, що рух не на порожньому ринку) + RSI(14)
перегрітий (≥70-75). **Критичний ризик-гейт:** funding rate ≤ −2% після
пампу — це НЕ підтверджує шорт, а ВИКЛЮЧАЄ пару зі списку шорт-
кандидатів. Логіка користувача: екстремально негативний funding після
пампу означає, що вже багато шортистів У ПОЗИЦІЇ (натовп), яких може
"винести" (short squeeze) — відкривати новий шорт проти вже
перевантаженого натовпу шортистів небезпечно, а не безпечно.

**Третій кошик — "спостереження" (не лонг, не шорт):** та сама
ситуація (памп + критично негативний funding), що виключається з
шортів, НЕ відкидається зовсім — переходить у окремий список
"спостереження". Логіка користувача: така монета цікава сама по собі
(велика вірогідність активності маркет-мейкера/маніпуляції на тлі
скупчення шортистів) — підхід до аналізу інший (не автоматичний
напрямок сигналу, а окрема увага), тому не фільтрується геть, а
позначається окремою категорією.

**Заборонені формулювання (analysis/CLAUDE.md, без винятку і тут):**
результат — "бичачий нахил"/"ведмежий нахил"/"спостереження",
НІКОЛИ "купуй"/"шорти"/"входь у позицію". Той самий стиль, що вже
`direction: up/down/neutral` у news_synthesis/market_synthesis.

**Побудова — поетапно (той самий принцип, що forecasting/: спершу одне
джерело наскрізно, довести підхід, потім розширювати), а не все одразу:
1. Адаптер Binance Futures (universe-лістинг + OI + funding rate +
   24h-тікер) — перший конкретний крок.
2. Bybit/OKX Futures адаптери, той самий інтерфейс, агрегація.
3. RSI/тренд-обчислення поверх уже готового `forecasting/trend.py`.
4. Три скринінг-скрипти (long/short/watch) з тестами на backtest-
   логіці, де застосовно.
5. Зберігання (нова таблиця) + Telegram-сповіщення + оркестрація.

**Крок 1-2 реалізовано (2026-09-27):** `crypto/binance_futures_adapter.py`,
`crypto/bybit_futures_adapter.py`, `crypto/okx_futures_adapter.py` —

### 2026-09-28: двошвидкісна архітектура — денний відбір (1д) + погодинний моніторинг кандидатів (1г)
**Проблема, поставлена користувачем:** денний таймфрейм прийнятний для
широкого сканування ринку (дешево, раз на добу), але для самого
стеження за вже знайденими пампами (кандидати на SHORT) — занадто
повільний. Шиткоїн може пампнути й здутись за кілька годин; поки денна
джоба помітить зміну OI наступного дня, сетап давно зіграв.

**Рішення (узгоджено з користувачем):** не переводити ВЕСЬ скринінг на
годинник (дорого — 1000+ символів щогодини), а розділити на дві
швидкості:
1. **Денний скан** (`run_screening.py`, без змін по суті) — Tier A +
   перевірка пампу по всьому ринку. Будь-який Tier A-символ з пампом
   ≥30% тепер ще й заводиться в новій таблиці `crypto_screening_candidates`
   (`upsert_candidate()`) — не одноразовий результат, а стан, що живе
   між прогонами.
2. **Погодинний моніторинг** (`monitor_candidates.py`, новий) — раз на
   годину проходить ЛИШЕ активні записи з `crypto_screening_candidates`
   (одиниці-десятки, не тисячі — дешево). Для кожного рахує SHORT/WATCH
   заново зі свіжими даними.

**Дельта без фіксованого вікна годин (пряма вимога користувача:
"тримати монету в статусі, поки дані відповідають", без таймера):**
`oi_change_pct`/`volume_spike_pct` рахуються не за "останні N годин", а
як зміна від того, що зафіксовано МИНУЛОГО разу — `last_oi_usd`/
`last_quote_volume` зберігаються прямо в рядку кандидата й
перезаписуються після кожної перевірки. Перший знімок — момент, коли
`run_screening.py` завів кандидата (не null, є з чого рахувати вже на
першому погодинному прогоні).

**Коли кандидат закривається (`status='closed'`):** ЛИШЕ коли сам памп
вичерпався (поточний памп впав нижче 30%) або символ зник з
агрегованого знімку. Поки памп тримається, кандидат лишається активним
незалежно від SHORT/WATCH-результату конкретної перевірки — "none"
(критерії виснаження ще не підтвердились) не закриває, а лишає
`status='candidate'` для наступної години.

**Чому нова таблиця, а не `screening_results`/`candidate_assets`
(append-only знімки, вже є в проєкті):** тут потрібен МУТАБЕЛЬНИЙ стан
(один рядок оновлюється багато разів, статус рухається
candidate→short/watch або candidate→closed) — ближче до `release_log`
(pending→detected→processed), не до append-only списків.

**Оркестрація:** `crypto_screening_daily`@6:25 (+15хв після
`crypto_derivatives_collect`@6:10 — дає час свіжій історії
зафіксуватись), `crypto_candidates_monitor`@:30 щогодини.

**Live-прогін підтверджено (2026-09-28):** `run_screening.py` завів
QNTUSDT кандидатом (памп 49.16%, funding низький). `monitor_candidates.py`
через деякий час порахував реальну дельту від знімку детекції — вивід
"немає сплеску обсягу" (не "немає даних") підтверджує, що OI/RSI-
критерії пройшли перевірку, лише обсяг не підтвердив — статус лишився
`candidate`, монета далі спостерігається наступної години.

**Тести:** `analysis/tests/test_monitor_candidates.py` (monkeypatch,
6 сценаріїв: немає кандидатів, символ зник, памп вичерпався, немає
історії ще, підтверджений SHORT, критичний funding → WATCH).

### 2026-09-29: UPSERT-и news_synthesis/market_synthesis/candidate_assets не скидали notified_at — свіжий повторний синтез того самого дня мовчки губився
**Живий фідбек користувача:** ручний прогін `analysis/news_analysis/
synthesize.py` порахував ЗОВСІМ НОВИЙ аналіз xauusd (direction=down,
confidence=0.85, зовсім інший від ранкового) — одразу після цього
`reporting/synthesis_notify.py` сказав "Нових синтезів немає".

**Причина:** усі три "один рядок на день" UPSERT-и в
`analysis/news_analysis/_db.py` (`save_synthesis` → `news_synthesis`,
`save_market_synthesis` → `market_synthesis`, `save_candidate` →
`candidate_assets`) мають `ON CONFLICT (..., день) DO UPDATE SET ...,
created_at = now()`, але жоден не скидав `notified_at`. Актив уже
надіслано вранці (`notified_at` проставлено) → рядок оновлюється новим
вмістом того самого дня → `notified_at` лишається СТАРИМ →
`WHERE notified_at IS NULL` у відповідному notify_*-скрипті більше
ніколи не бачить рядок аж до наступної календарної доби, хоча контент
за суттю новий. Точний антипод бага з `daily_digest.py` вище того ж
дня: там дублювало вже надіслане, тут — навпаки, ховає справді нове.

**Фікс:** усі три `DO UPDATE SET` тепер додатково скидають
`notified_at = NULL` — оновлений рядок знову стає "ще не надісланим",
і найближчий notify_*-прогін підхопить свіжий вміст.

**Тести:** `analysis/tests/test_news_analysis_db.py` (новий) —
фейковий cursor/conn (той самий підхід, що `test_consolidated_db.py`),
перевіряє фактичний SQL усіх трьох UPSERT-ів на `notified_at = NULL` у
SET-частині (не в INSERT-частині — там скидати нема чого).

### 2026-10-02: синтез ціна/новини залежав ЛИШЕ від новин — рух ціни без новини ніколи не перевірявся
**Живий фідбек користувача:** "ти маєш відслідковувати і рух ціни
аномальний для активу і впливові новини. коли або одне або друге є
суттєве, ти робиш аналіз... і відправляєш в телеграм" — новинна
класифікація/агрегація (`relevance_filter.py`/`aggregate.py`) лишається
як є ("з ними було все добре"); проблема саме в тому, що ТРИГЕР
синтезу (`synthesize.py`) був жорстко прив'язаний до наявності
новинного сигналу — `aggregate_by_asset()` повертає сигнал лише для
активів, згаданих хоч в одній релевантній статті; актив без жодної
новини НІКОЛИ навіть не перевірявся на ціну, хай би який різкий був
рух.

**Рішення:** OR-логіка. Універсум активів = watchlist
(`news/queries.py:WATCHLIST_ASSET_IDS`) + поточний скринінг акцій
(`screening._results_db.fetch_latest_tickers`) + усе, що вже має
новинний сигнал. Актив синтезується, якщо є новинний сигнал (як і
раніше, без змін до фільтра значущості) **або** рух ціни
`prices.py:is_anomalous_move()` визнає аномальним.

**"Аномальний" — відносно власної історичної волатильності активу, не
фіксований %:** `|pct_change за вікно| ≥ 2.0 × (денний stdev активу ×
√window_days)`. Відкинуто єдиний фіксований % для всіх активів —
крипта рутинно рухається на 5%+ (дав би постійний шум), золото/EURUSD
рідко рухаються на кілька % навіть за тиждень (дав би глухоту).
Константи (`prices.py`): `ANOMALY_SIGMA_MULTIPLIER=2.0`,
`ANOMALY_MIN_HISTORY=10` (денних доходностей, менше — "не досить даних
судити", чесне `False`, не хибне спрацювання), `ANOMALY_HISTORY_LOOKBACK=90`.
Це сповіщувальний порІг, не прогнозна модель — критерій "б'є naive"
(analysis/CLAUDE.md, forecasting/) сюди не застосовний; множник 2.0 —
емпіричний старт, не backtest, переглянути після накопичення живих
спрацювань/пропусків.

**Коли новин немає, але ціна аномальна:** LLM отримує "порожній"
сигнал (0 історій) замість дампу нульового `direction_counts`
(`build_prompt()`), і `SYSTEM_PROMPT` явно каже: поясни рух БЕЗ
новинної причини як таку — сам факт відсутності новин на аномальний
рух вже інформація (технічний рух / новина ще не вийшла), не привід
мовчати.

**Побічний фікс:** `ASSET_PRICE_SOURCES` тепер містить джерела
`binance`/`coingecko` (btc/eth/sol/xagusd, вище) — `orchestration/
jobs.py:_watchlist_prices()` ітерує саме цей словник і раніше логував
би хибне "невідоме джерело" на ці чотири активи щодня (ту джоба їх не
збирає, `_crypto_prices()` збирає окремо, щогодини) — додано явний
`_CRYPTO_OWNED_SOURCES`-пропуск без попередження.

**Тести:** `analysis/tests/test_prices.py` (`fetch_price_history`,
`is_anomalous_move` — достатньо/замало історії, нульова волатильність,
рух у межах/поза межами норми), `analysis/tests/test_synthesize.py`
(`build_prompt` явно каже "новин не знайдено" при `cluster_count=0`).

### 2026-10-02: check_releases — щохвилини замість раз/15хв, буфер 30хв прибрано (користувач: "сама логіка джоби неправильна")
**Контекст:** живий фідбек користувача на попередній фікс (heartbeat):
"ми кожен понеділок збираємо календар на тиждень з часом виходу

живий і реліз вийшов точно за розкладом.

**Дві архітектури розглянуто** (користувачу прямо пояснено
ресурси/швидкість обох):
- **А (обрано):** лишити `check_releases` єдиною статичною cron-джобою,

  статичні джоби) не змінюється.
- **Б (відхилено):** `refresh_calendar.py` сам реєструє в APScheduler
  one-off інтервальні джоби на кожен реліз тижня (старт точно о
  scheduled_at, раз/хв чи частіше, до detected або timeout) — вимагає
  persistent jobstore (SQLAlchemy поверх тієї самої Postgres/Timescale)
  замість поточного in-memory, бо subprocess-джоба (refresh_calendar)
  не може напряму додати job у ЖИВИЙ BlockingScheduler іншого процесу.
  Дає ту саму швидкість детекції (~1 хв), виграє лише якщо потрібна
  точність тісніша за хвилину — суттєво складніше за еквівалентний
  практичний результат, користувач обрав А.

scheduled_at і далі щохвилини, доки джерело не опублікує; затримка
публікації сама по собі не помилка, просто кілька порожніх спроб
поспіль).

**Побічний ефект — ВИПРАВЛЕНО того самого дня (користувач, прямо

вікна. Порядок виконання в межах ОДНІЄЇ хвилини тепер тримається на

### 2026-10-02: живий баг — Binance OI додавався ПІСЛЯ Tier A, тож символи з недостатнім Bybit/OKX OI відсіювались ще до шансу пройти з повним трибіржовим OI

(SHORT/WATCH очікувано мав хоча б завести кандидата), але `run_screening.py`

`scripts/_debug_magmausdt.py`) показала: Tier A ВІДХИЛИВ символ через
недостатній OI — хоча реальний сукупний OI (Bybit $4.4М + Binance

окремого per-symbol запиту (`fetch_open_interest()`), і цей запит

пройшли Tier A без нього ("не для всього ринку, лише для виживших" —
навмисна оптимізація, щоб не бити Binance ~1045 запитами). Побічний
ефект, не передбачений у вихідному дизайні: якщо сам Bybit+OKX OI
символу нижче `MIN_OPEN_INTEREST_USD`, символ ВІДСІЮВАВСЯ Tier A ще
ДО того, як міг отримати шанс пройти з повним (трибіржовим) OI —
MAGMAUSDT не на OKX взагалі, тож Bybit-лише OI ($4.4М) не дотягував
до порогу самостійно.

**Фікс:** перед фінальним Tier A-фільтром — окремий прохід, що шукає
символи, які провалюють Tier A САМЕ через OI (підстановка штучно
величезного OI в пробну копію даних — якщо це змінює вердикт, OI
справді єдина причина; інші критерії далі перевіряються як є). Для
НИХ (не для всього ринку) і лише якщо є дані з Binance — дістати
Binance OI ЗАРАЗ і додати до агрегованого OI ПЕРЕД фінальним Tier A.
`binance_oi_cache` запам'ятовує, кому вже додано Binance OI на цьому
кроці, щоб наступний (вже існуючий) прохід `enrich_with_binance_oi()`
(для ВСІХ Tier A-виживших, потрібен для `last_oi_usd`-засіву
кандидата) не додав Binance OI вдруге (`+=` там підсумовує, не
замінює).

**Чому не збагачувати Binance OI для ВСЬОГО ринку одразу (простіший
варіант):** ~1045 зайвих запитів замість кількох прикордонних —
навмисна оптимізація вихідного дизайну лишається, фікс лише звужує
"ліниве" збагачення до дійсно потрібних випадків, не прибирає його.

тепер ОДНЕ з двох:** сплеск обсягу (як було) **АБО** різке падіння
ціни за годину (`HOURLY_PRICE_DROP_PCT = -5.0`, новий config.py) — OI-
падіння й RSI-перегрітість лишаються обов'язковими в обох випадках,
змінився лише "третій" критерій підтвердження з єдиного на
альтернативний (`OR`, не `AND`).

**Чому саме Binance mark_price, не ціна з іншої біржі:** єдине
джерело РЕАЛЬНОЇ ціни (не лише %-зміни) в агрегованому знімку — Bybit/
OKX у `per_exchange` несуть тільки `price_change_percent`, не саму
ціну (docstring `aggregate_sources.py`). Той самий Binance-залежний
компроміс, що вже є для RSI/тренду (`compute_price_indicators`,
`fetch_klines`) — символи поза Binance лишаються без цього сигналу
(не ламаються, просто `price_change_pct_1h` завжди `None` для них,
як і RSI).

**Тести:** 3 нові в `test_short_watch_screen.py` (SHORT через
погодинне падіння без сплеску обсягу; "none" коли ні те, ні те не
підтверджує; старий шлях через сплеск обсягу й далі працює сам) + 1
інтеграційний у `test_monitor_candidates.py` (повна прокладка
`candidate["last_price"]` → `price_change_pct_1h` → SHORT, і що нова
`last_price` коректно записується для наступної години).
