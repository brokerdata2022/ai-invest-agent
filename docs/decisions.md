# Журнал рішень (ADR-лайт)

Формат кожного запису: дата, що вирішили, чому, які альтернативи відкинули.
Мета — щоб через 3 місяці (або нова сесія Claude) не довелось заново
переосмислювати "а чому ми взагалі так зробили". Повні версії записів
(з деталями діагностики, живих прогонів, стек-трейсів) — в
`docs/archive/decisions-full-2026-08-09.md`.

### 2026-08-27: Стек — Python + PostgreSQL/TimescaleDB
**Рішення:** Python як мова бекенду; PostgreSQL + TimescaleDB як єдина
БД (замість окремих time-series і реляційної СУБД).
**Чому:** один інструмент для часових рядів і реляційних даних —
менше операційної складності; обидва компоненти безкоштовні.

### 2026-08-27: Джерела даних — пріоритет безкоштовних першоджерел
**Рішення:** FRED/ECB SDW (макро), SEC EDGAR (звіти компаній),
yfinance (ціни), CoinGecko + Binance (крипта), GDELT + офіційні RSS
(новини). Повний список — `data-ingestion/CLAUDE.md`.
**Чому:** максимальне покриття безкоштовно, з пріоритетом офіційних
першоджерел там, де вони існують.
**Відкинуто:** Alpha Vantage як основне джерело цін акцій — 25
запитів/день, замало навіть для помірного покриття.

### 2026-08-27: Календар релізів з рівнем впливу — власна розмітка
**Рішення:** дати релізів — з офіційних графіків (BLS/BEA/Fed/ECB),
рівень впливу (High/Medium/Low) — власний статичний список.
**Чому:** офіційного безкоштовного API з готовою розміткою впливу не
існує (ForexFactory та подібні — неофіційні); розмітка "що є
high-impact" загальновідома і рідко змінюється.

### 2026-08-29: Новий адаптер = новий рядок у sources + перевірка кожного series key живим запитом
**Рішення:** при додаванні адаптера нового джерела обов'язково:
1) рядок у seed `INSERT INTO sources` (db/schema.sql); 2) кожен
series key перевірити живим запитом до live-тесту користувача.
**Чому:** обидва ризики виявились реальними на ecb_adapter.py —
відсутність джерела в `sources` ловиться тільки на реальному insert
(`ForeignKeyViolation`), а series key з непрямих джерел (старі
довідники, статті) виявився застарілим (404).
**Відкинуто:** довіряти юніт-тестам на фікстурах як доказу готовності
до live-тесту — вони перевіряють тільки `normalize()`, не існування
джерела в БД чи актуальність зовнішнього API.

### 2026-08-29: raw_observations зберігає тільки сирі значення, не % зміни
**Рішення:** data-ingestion/ ніколи не рахує похідні величини (MoM/YoY
% зміна) — тільки сире значення від джерела. Розрахунки — в analysis/.
**Чому:** з сирого індексу можна порахувати будь-яку зміну на вимогу;
зберігання готового % ламає коректну обробку ревізій (від якої версії
минулого значення рахувати %?).
**Відкинуто:** тягнути з FRED готові `units=pch/pc1` як окремі
metric_id — дублює дані й прив'язує до методології FRED.

### 2026-08-29: Виправлення — partition column для hypertable — observed_at, не fetched_at
**Рішення:** raw_observations партиціонується по `observed_at`, не
`fetched_at` (як було спочатку).
**Чому:** `create_hypertable()` вимагає, щоб УСІ unique-обмеження
включали колонку партиціювання; наш `UNIQUE(source, metric_id,
observed_at, revision)` не містив `fetched_at` — hypertable не
створювався, init-скрипт падав з `ForeignKeyViolation`. `observed_at`
уже в цьому UNIQUE, і це природніша вісь для типових запитів analysis/
("дані за період X", не "коли дізнались").

### 2026-08-29: Revision обчислює шар збереження, не адаптер
**Рішення:** адаптери завжди повертають `revision=None`; фактичний
номер визначає `common/db.py:decide_revision()` під час запису —
порівнянням з останнім збереженим значенням.
**Чому:** визначити ревізію можна лише знаючи історію, а адаптер не
повинен звертатись до сховища (docs/architecture.md); чиста функція
без SQL дозволяє тестувати логіку без реальної БД.
**Відкинуто:** давати адаптеру доступ до БД для самовизначення ревізії
— порушує розділення "адаптер тільки збирає", ускладнює тестування.

### 2026-08-30: "Живий запит повернув 200 OK" ≠ "series key досі актуальний"
**Рішення:** якщо отримане значення застаріле більш ніж на один
звітний період — перевіряти, чи датасет не замінено/закрито джерелом,
а не шукати баг у логіці фільтрації.
**Чому:** `eurozone_hicp` через flowRef `ICP` стабільно повертав 200 OK
і коректні записи, але дані завмерли на грудні 2025 — ECB тихо закрив
датасет `ICP` (методологічна реформа) і замінив `HICP` з іншим кодом
джерела в ключі серії. Запит до старого flowRef не падав помилкою —
просто не отримував нових спостережень. Виправлено:
`eurozone_hicp` → `HICP.M.U2.N.000000.4D0.ANR`.

### 2026-08-30: Китай і Індію остаточно не розглядаємо
**Рішення:** макро-Азія обмежується Японією; Китай (NBS/PBOC) і Індія
(RBI/MOSPI) виключені остаточно — рішення користувача, не тимчасове
відкладення.
**Чому:** жодне джерело не має задокументованого публічного REST API
(`data.stats.gov.cn`, `dbie.rbihub.in` розраховані на ручний
перегляд/Excel, не програмний доступ).

### 2026-08-30: Японія CPI — теж пройшла базову ревізію 2026 року
**Рішення:** e-Stat CPI — `statsDataId 0004052037` (2025=100, чинний з
21.08.2026), не `0003427113` (2020=100).
**Чому:** Statistics Bureau of Japan провела базову ревізію ІСЦ, як і
Eurostat для HICP; старий `statsDataId` не видає помилку, просто не
отримує нових спостережень після перехідного періоду — той самий
"тихий" режим відмови, що й ICP→HICP.

### 2026-08-30: USD/JPY (carry trade) — обрано FRED (DEXJPUS), не BOJ FM08
**Рішення:** `macro/fred_adapter.py`, metric_id `usdjpy_fx_rate`, FRED
series `DEXJPUS`.
**Чому:** серія релізу Fed H.10, того самого типу джерела, що вже
перевірені fed_funds_rate/treasury_10y — уникнення другої
неперевіреної структури відповіді (BOJ FM08) поряд із BOJ FM01.

### 2026-08-30: e-Stat — коди area/cat01 резолвляться в рантаймі, не хардкодяться
**Рішення:** `macro/estat_adapter.py` робить попередній meta-запит
(`metaGetFlg=Y&limit=1`), знаходить коди area/cat01 за
людинозрозумілою назвою ("全国"/"総合"), тільки тоді робить основний
запит.
**Чому:** на відміну від FRED/ECB/BOJ, у e-Stat потрібний зріз
визначається кодами класифікації, задокументованими лише як
таблиця-додаток до кожного датасету окремо (мережа розробки не мала
прямого доступу до e-stat.go.jp для збору кодів наперед). Резолюція
за назвою стійкіша до того, що коди різняться між `statsDataId`.

### 2026-09-13: japan_cpi — знайдено і виправлено реальний баг з виміром `tab`
**Рішення:** `_resolve_area_and_cat01()` → `_resolve_dimensions()` —
резолвить УСІ виміри таблиці (не тільки area/cat01) через новий
словник `_DIMENSION_PREFERENCES`; якщо для виміру з кількома
значеннями немає запису — явний `ValueError`, а не мовчазне змішування.
**Чому:** live-прогін показав "фальшиві ревізії" — той самий день мав
кілька різних значень підряд (`101.5 → 0.5 → 1.5`). Причина: таблиця
CPI публікує кілька рядків на місяць під різними кодами `tab` (рівень
індексу окремо від %-зміни р/р і м/м) — без фільтрації за `tab` усі
три потрапляли в один `metric_id` і перезаписували одне одного як
"ревізії", хоча це три різні величини.
**Другий шар захисту:** `normalize()` дедуплікує по `observed_at` —
конфлікт логується `WARNING`, не пишеться мовчки.
**Відкрите питання:** `run_collect.py`/`collect_all.py` вважають запис
успішним, якщо `store()` не впав винятком, навіть якщо кілька revision
для однієї дати в одному прогоні — ознака проблеми з джерелом, а не
легітимна ревізія. Розглянути поріг-попередження на рівні collect_all.py
(не зроблено).

### 2026-09-14: companies/ (SEC EDGAR) — спершу скринінг акцій, потім збір даних
**Рішення:** перед побудовою `companies/`-адаптера спершу визначити й
задокументувати критерії відбору акцій (`docs/screening-criteria.md`).
`companies/` збиратиме дані тільки по вже відфільтрованому списку, не
довільному watchlist. `METRICS` — словник концептів (us-gaap tags), а
не фіксованих показників; тикер — параметр виклику; CIK резолвиться
через bulk `company_tickers.json`.
**Чому:** мета проєкту — знаходити кандидатів за критеріями, а не
моніторити довільний топ-N компаній; спершу потрібен сам скринер.
**Відкинуто:** захардкодити 2-3 тикери як seed — не відповідає меті.

### 2026-09-14/20: Джерело котирувань — Stooq → Alpaca → Stooq → Twelve Data
**Рішення (фінальне):** **Twelve Data** — ціна/обсяг акцій для
скринінгу (`quotes/twelvedata_adapter.py`). Universe — S&P 500 з
community-датасету constituents.csv, CIK резолвиться напряму з нього
(без окремого лукапу на тикер).
**Чому саме такий шлях:**
1. **Stooq** (перший вибір) — без ключа й реєстрації, здавався
   найпростішим.
2. **→ Alpaca Markets** — закривав і котирування, і universe одним
   джерелом; відкинуто: сайт/API географічно недоступні з України
   (недокументований гео-блок), а сам факт вимагав реєстрації
   реального акаунту.
3. **→ Stooq знову** + SEC `company_tickers_exchange.json` для universe
   (без акаунтів). Живий тест: `delimiter=";"` (польський регіональний
   формат CSV), не `,` — виявлено тільки через реальний файл від
   користувача, не через пошук у вебі.
4. **→ Twelve Data (фінально)** — Stooq відкинуто остаточно: JS-based
   бот-захист (Cloudflare-подібний) віддає HTML-сторінку верифікації
   замість CSV при запиті без browser-like User-Agent; `requests` не
   може це пройти без headless-браузера. Twelve Data підтверджено
   живим запитом користувача (email+пароль, без капчі, ключ одразу в
   кабінеті; ~8 запитів/хв, 800/добу; помилки — HTTP 200 з
   `status:"error"` в тілі, не HTTP-кодом).
**Урок:** для будь-якого джерела "без реєстрації/без ключа" — попросити
живу перевірку одним запитом ДО написання адаптера; вебпошук про
поведінку зовнішнього API не заміняє реального запиту чи файлу
(тричі підряд один живий тест дав більше сигналу, ніж година пошуку).
**Universe:** S&P 500 (не весь `company_tickers_exchange.json`, кілька
тисяч тикерів) — вже попередньо якісний ліквідний пул, і суттєво
менше запитів за прогін скринера.

### 2026-09-20: Пороги Tier A–C, ребалансування, composite score, news-канал (фінально)
**Рішення (пороги):**
- Tier A (ліквідність): NYSE/NASDAQ, ціна > $10, капіталізація > $10
  млрд, середній $ обсяг (63 дні) > $10 млн/день.
- Tier B (фундаментал): NetIncomeLoss > 0 останні 4 квартали, revenue
  YoY > 10%, EPS diluted YoY > 15%, шери в обігу не зросли > 3% YoY,
  Liabilities/Assets < 0.6.
- Tier C (valuation): P/E ∈ (10, 35), P/S < 8, PEG < 2.
**Чому такі числа:** планка піднята проти чернетки — свідомо "топові"
large-cap growth-кандидати, а не просто "не мікрокап" (деталі
обґрунтування кожного порогу — `docs/archive/decisions-full-2026-08-09.md`).
**Ребалансування:** синхронно зі звітністю — перезбір щокварталу
(цикл 10-Q).
**Composite score:** `0.35×percentile(revenue_growth) +
0.30×percentile(eps_growth) + 0.20×percentile(-P/E) +
0.15×percentile(avg_dollar_volume)`, percentile — серед кандидатів, що
пройшли hard-фільтри в поточному прогоні (не серед усього S&P 500).
**News-канал:** акції з новин (майбутній `news/`, GDELT) можуть
потрапити в список поза чергою, але тільки ПІСЛЯ проходження Tier B —
новинний привід сам по собі не причина додавання, лише тригер
позачергової перевірки.

### 2026-09-20: companies/sec_edgar_adapter.py написано
**Рішення:** `METRICS` — словник концептів (us-gaap/dei tag), тикер —
параметр конструктора, CIK через `company_tickers.json` (кеш на
процес). `normalize()` фільтрує XBRL duration-концепти за довжиною
періоду (75-100 днів) — лишає тільки квартальні, відкидає кумулятивні
(той самий клас захисту, що вже застосований у `estat_adapter` після
багу з japan_cpi, тепер зроблений наперед).
**Чесно позначено нетестоване:** формат companyconcept підтверджено
незалежними технічними джерелами, але не живим запитом —
`sec.gov`/`data.sec.gov` недоступні з мережі розробки. Перший прогін
користувача — фактична перевірка.

### 2026-09-21: sec_edgar_adapter — дедуплікація дублікатів по даті
**Рішення:** коли кілька записів SEC припадають на одну дату,
береться той, що з найпізнішим `filed` (найактуальніше подання),
решта відкидається.
**Чому:** живий тест на AAPL показав "ping-pong" ревізії — той самий
день то `1.97`, то `13.81` (EPS diluted за 2012-12-29). Причина: SEC
інколи повертає два записи з різним `val` для того самого кварталу —
пізніше подання перераховує EPS минулих періодів під нову к-сть акцій
після спліту. Попередній фільтр (форма + тривалість періоду) цього не
ловив — той самий клас проблеми, що й `japan_cpi`/`tab` (2026-09-13),
інша конкретна причина.
**Свідомий компроміс:** беремо найактуальніше подання, не "як
спочатку повідомлено" — для growth-скринінгу порівнянність цифр у
одних одиницях важливіша за точну відповідність оригінальній
публікації.

### 2026-09-24: revenue-тег застарів для AAPL — multi-tag fetch до Tier B
**Рішення:** `METRICS` — `dict[str, list[tuple[taxonomy, tag]]]`
замість одного тега на концепт; `revenue` фетчить і `Revenues`, і
`RevenueFromContractWithCustomerExcludingAssessedTax`, зливає через ту
саму дедуплікацію по даті (найпізніший `filed` виграє), що вже існує

**Чому:** `aapl_revenue` зупинявся на 2018-09-29 — AAPL (і, ймовірно,
велика частка компаній) перейшли на новий тег пост-ASC 606, стара
позначка перестала оновлюватись. Виправлено ДО живого прогону Tier B,
а не постфактум.
**Не зроблено:** такий самий fallback для shares_outstanding (запис
вище) — окрема нерозв'язана задача.

### 2026-09-24: analysis/screening/tier_b.py — перший багатокроковий скринінг-код
**Рішення:** `passes_tier_b()` — чиста функція, приймає часові ряди
(net_income, revenue, eps, shares) і останні значення
(liabilities, assets). YoY — (найновіше − рік_тому)/|рік_тому|, пошук
"запису рік тому" в межах ±20 днів навколо 365 (квартали не завжди
рівно 91.25 дні між компаніями). Порядок перевірки: profitability →
revenue YoY → EPS YoY → dilution → L/A, рання зупинка на першому
провалі.

### 2026-09-25: Виправлено N+1 SQL-запити в analysis/screening/ — batch-запити замість запиту на кожен тикер
**Що сталось:** живий прогін tier_a.py зайняв ~9.5 хв на 491 тикер;
tier_b.py — ще довше (перевіряє 6 SEC EDGAR концептів на тикер).
Причина — не розмір результату, а те, що `v_current_values`/
`v_observations_latest_revision` — DISTINCT ON-views над TimescaleDB
hypertable з дрібним (дефолтним) chunk_time_interval: для тикерів з
десятиліттями історії (Twelve Data) це тисячі чанків, і кожен окремий
запит без обмеження по `observed_at` змушений перевірити кожен чанк —
фіксовані накладні витрати ~100-150мс НЕЗАЛЕЖНО від розміру
результату. tier_a.py робив 3 запити/тикер, tier_b.py — 6/тикер:
491-411 тикерів × (3-6) запитів = 1500-2500+ послідовних запитів.
**Рішення:** новий спільний модуль `analysis/screening/_batch_db.py`
— `batch_latest_values()`/`batch_series()` беруть СПИСОК metric_id і
роблять ОДИН запит (`WHERE metric_id = ANY(список)`) замість запиту
на кожен. Накладні витрати сканування чанків платяться один раз для
всього списку тикерів, а не N разів. tier_a.py: 3×N → 4 запити
загалом. tier_b.py: 6×N → 6 запитів загалом. tier_c.py: 2×N → 2
запити загалом.
**Побічний фікс (той самий корінь, редундантний перерахунок):**
`tier_b.py`/`tier_c.py`/`composite_score.py` за замовчуванням (без
явно переданих `tier_a_results`) кожен викликав `run_tier_a()` ще раз
із нуля, навіть якщо виклик уже мав готовий результат вище по
ланцюжку — повний прогін `composite_score.py` рахував Tier A ДВІЧІ.
Виправлено: `tier_a_results`/список тикерів тепер прокидається вниз
по ланцюжку (`run_tier_c()`→`run_tier_b(tier_a_tickers=...)`,
`run_composite_score()`→те саме).
**Чисті функції не змінились:** `passes_tier_a/b/c`, `yoy_growth`,
`ttm_sum`, `all_positive_last_n` — без змін, ті самі пороги, той самий
результат. Новий тестований пурум-хелпер:
`avg_dollar_volume_from_series()` (заміняє SQL JOIN...AVG() з
попередньої версії _avg_dollar_volume()) — 4 нових тести в
test_tier_a.py.
**Не зроблено (окрема, більша задача):** сам chunk_time_interval
hypertable не змінено (дефолтний, дуже дрібний для цього типу даних)
— це вимагало б міграції існуючих чанків, ризикованіше й не потрібне
після фіксу N+1 (batch-запити роблять цю накладну вартість
одноразовою на весь прогін, а не помножену на к-сть тикерів).

### 2026-09-25: batch_ticker_names() — GDELT відхиляє й занадто КОРОТКИЙ query, не тільки довгий
**Що сталось:** живий прогін (вище, після фіксу з insert-per-batch)
показав групу 3/3 — `("TE Connectivity" OR "Uber" OR "Wabtec")`, 41
символ — GDELT відхилив з `"The specified phrase is too short."`.
Той самий текст помилки ("too short or too long"), що й для 294-
символьного query 2026-09-25 вище — підтверджує: GDELT перевіряє
ДІАПАЗОН довжини query, не тільки стелю. Жадібне заповнення в
`batch_ticker_names()` лишало "хвіст" (залишок після заповнення
попередніх груп до максимуму) неконтрольовано малим.
**Рішення:** новий `MIN_QUERY_LEN = 70` (запас над підтвердженим
збійним 41, з запасом під підтверджений робочий 117) і крок після
жадібного заповнення: якщо запит ОСТАННЬОЇ групи коротший за поріг —
зливається з попередньою групою (а не лишається окремим приреченим
запитом). Останній батч після цього може перевищити `MAX_QUERY_LEN`
(до ~150+70=220 у гіршому разі) — це свідомий компроміс: 220 суттєво
нижче підтвердженого збійного 294, тобто безпечніше за гарантоване
"too short".
**Офіційно не задокументовано:** ні верхня, ні нижня межа не
описані GDELT (перевірено — `blog.gdeltproject.org/gdelt-doc-2-0-api-debuts`
згадує тільки ліміт MAXRECORDS, нічого про довжину query) — обидва
пороги емпіричні, засновані виключно на живих прогонах цієї сесії.

### 2026-09-25: MIN_QUERY_LEN — спростовано як причина; реальна проблема — слово "Uber"
**Що сталось:** наступний живий прогін (після мерджу "хвоста", вище)
дав групу 2/2 — `("Huntington Ingalls Industries" OR ... OR "Uber" OR
"Wabtec")`, **175 символів** (вище і MIN_QUERY_LEN=70, і підтвердженого
робочого 117-150) — GDELT ЗНОВУ відхилив тим самим `"The specified
phrase is too short."`. Це прямо спростовує гіпотезу "довжина query"
— 175-символьний query не може бути "занадто коротким" за жодним
розумним визначенням. Єдине спільне між обома збоями (41 і 175
символів) — термін `"Uber"`. Інші короткі однослівні терміни в тих
самих групах ("Emcor" 5 літер, "Wabtec" 6, "Casey's") — жодного разу
не викликали цю помилку.
**Урок (за прямою вимогою користувача "не змінюй код на вгад"):**
перша гіпотеза (MIN_QUERY_LEN) була побудована на ОДНОМУ, сплутаному
прикладі — єдиний короткий query, який на той момент тестувався,
випадково містив і "Uber". Другий живий прогін з контрольованою
змінною (довжина зросла до 175, "Uber" лишився) ізолював справжню
причину. `MIN_QUERY_LEN`/`batch_ticker_names()` merge-крок НЕ
видалено (шкоди не завдає, залишається як захисна евристика "про
всяк випадок"), але коментарі в коді відверто позначають його як
непідтверджений, щоб наступна сесія не сприйняла його як факт.
**Рішення:** `STOCK_NAME_OVERRIDES` — курований словник (той самий
підхід, що й `WATCHLIST_TERMS`/FRED `METRICS`) — для тикера UBER
термін замінюється на повну назву `"Uber Technologies"`. GDELT сам
документує відхилення "дуже коротких АБО дуже загальновживаних" слів
навіть у лапках — "uber" загальновживане англійське слово (підсилювач),
на відміну від специфічних "Emcor"/"Wabtec". Точний критерій
"загальновживаності" GDELT не описує, тому фіксуємо підтверджений
конкретний випадок явно, а не намагаємось вивести загальне правило
з одного прикладу.
**Не перевірено (чесно позначено):** чи є в S&P 500 universe інші
тикери з такою самою проблемою (короткі загальновживані англійські
слова як офіційна назва) — `STOCK_NAME_OVERRIDES` розширюється по
факту виявлення, не проактивним аудитом усіх 500 назв.
**Live-підтвердження фіксу (2026-09-25):** повторний прогін з
`"Uber Technologies"` замість `"Uber"` (query групи 2 — 188 символів,
довше за попередній збійний 175) — жодного разу "too short" не
з'явилось. Група 1 пройшла повністю (75 статей); група 2 впала лише
на вичерпаному retry-бюджеті `429` (спільний dev-IP під важким
навантаженням після десятків запитів за сесію) — інший, вже відомий
клас проблеми, не пов'язаний з "Uber"/довжиною query. Разом:
75+150=225 статей у `raw_news` за сесію (watchlist-потік, обидва
джерела — run_collect_news.py і collect_stock_news.py).

### 2026-09-26: rss_adapter.py — .content (байти), не .text — UTF-8 BOM у Fed
**Що сталось:** перший живий прогін — ECB спрацював (15 записів), Fed
впав з "невалідний XML". Діагностика (`response.content[:200]`) —
Fed віддає тіло з UTF-8 BOM (`\xef\xbb\xbf`), але HTTP-заголовок
`Content-Type: text/xml` без `charset`; `requests.Response.text` у
цьому випадку вгадує `ISO-8859-1` (RFC-дефолт для text/* без
charset), BOM перетворюється на 3 сміттєвих символи `ï»¿` ПЕРЕД
`<?xml version=...`, і `ElementTree.fromstring()` відмовляється це
парсити (XML-декларація має бути найпершою).
**Рішення:** `fetch()` повертає `response.content` (сирі байти), не
`response.text` — `ElementTree` сам коректно визначає кодування й BOM
з байтів, без залежності від вгадування `requests`.
**Тест-регресія:** `test_normalize_handles_utf8_bom_bytes` — байти з
BOM-префіксом, той самий клас збою, що й реальний.
**Live-підтвердження фіксу (2026-09-26):** повторний запуск —
`fed_rss` 20 записів (успішно, фікс спрацював), `ecb_rss` 0 нових
(коректний дедуп — ті самі 15 записів, що й до фіксу). DeepSeek
(`run_news_analysis.py --stream geopolitical`) обробив усі 35 нових
RSS-статей без помилок — рішення з монетарної політики (FOMC,
central bank speeches) позначені релевантними, рутинні enforcement-дії
й банківські дозволи — ні, що збігається з очікуваним сигналом.

### 2026-09-26: news/ — фільтр свіжості (GDELT timespan + news_notify.py по published_at)
**Що сталось:** користувач переглянув кілька проаналізованих статей і
знайшов серед них липневу публікацію про рішення по ставці, яке вже
було прийняте у вересні — застаріла, а не актуальна інформація для
мети "розуміти поточний напрямок ринку" (docs/decisions.md, 2026-09-25
"news/ — обсяг..."). Корінь — два окремі пробіли:
1. `GdeltAdapter.fetch()` не обмежував query за часом (`maxrecords=75,
   sort=datedesc`, без `timespan`) — для вузьких query GDELT сягав
   місяцями назад, щоб набрати maxrecords збігів.
2. `reporting/news_notify.py:fetch_recent_relevant()` сортував за
   `a.created_at` (коли МИ проаналізували), не `n.published_at` (коли
   стаття ВИЙШЛА) — стаття, що пролежала в `raw_news` тижнями (append-
   only, rule 6, ніколи не видаляється) і проаналізована пізніше,
   виглядала б як "остання новина" в Telegram-дайджесті.
**Рішення:**
1. `GdeltAdapter.fetch(timespan="3d")` — новий параметр (GDELT DOC API
   підтримує `TIMESPAN`, підтверджено офіційним блогом
   `blog.gdeltproject.org/gdelt-doc-2-0-api-debuts`), дефолт 3 дні;
   `--timespan` прокинуто в `run_collect_news.py`/`collect_stock_news.py`.
2. `fetch_recent_relevant()` — `ORDER BY n.published_at DESC` (не
   `a.created_at`) + `WHERE n.published_at >= now() - max_age_days`
   (дефолт 7 днів, `--max-age-days` в CLI). Релевантна, але
   місяцями стара стаття тепер НЕ потрапить у сповіщення, навіть
   якщо проаналізована щойно.
**Чому не видаляємо старі рядки з raw_news/news_analysis:** rule 6
(CLAUDE.md) — ніколи не видаляти сирі зібрані дані. Старі записи
лишаються (аудит/історія), фільтр свіжості — тільки на рівні читання
(reporting/), не на рівні зберігання.

### 2026-09-26: relevance_filter.py — звужено критерій релевантності + опис статті в промпт
**Що сталось:** користувач переглянув живі результати аналізу й
оцінив забагато статей як "релевантних" без реального сигналу —
корінь: (1) `build_prompt()` давав DeepSeek ЛИШЕ заголовок (GDELT не
дає тексту статті взагалі; RSS дає `description`, але `fetch_unanalyzed()`
навіть не вибирав `raw_payload` з БД, і `build_prompt()` його не
використовував) — DeepSeek вгадував релевантність із заголовка, а
заголовки системно звучать "по темі", не несучи конкретного факту;
(2) `SYSTEM_PROMPT` не мав явного, перевіюваного критерію "що таке
реальна інформація" — тільки загальне "чи може вплинути на ціну".
**Рішення:**
1. `_db.py:fetch_unanalyzed()` — додано `n.raw_payload` у SELECT.
2. `relevance_filter.py:_extract_description()` — дістає `description`
   з `raw_payload`, якщо є (RSS-фіди, не всі); `build_prompt()` додає
   рядок "Опис: ..." коли є контент понад заголовок.
3. `SYSTEM_PROMPT` переписано з явним критерієм `is_relevant=true`
   лише для трьох конкретних категорій (економічний показник з
   цифрами/трендом; геополітична подія з прямим ринковим наслідком;
   конкретний вплив на ціну/тренд активу) і явним списком, що НЕ
   рахується (рутинні регуляторні дозволи, огляди без нових фактів,
   колонки думок, локальні новини без міжнародного виміру, PR без
   фінансової суті) — з правилом "сумніваєшся — false, не true".
**Не ретроактивно:** старі рядки `news_analysis` (проаналізовані до
цього фіксу) НЕ перераховуються — `fetch_unanalyzed()` бере тільки
статті БЕЗ рядка в `news_analysis`, а видаляти/переписувати старі
заборонено rule 6. Новий, строгіший критерій діє тільки на статті,
проаналізовані ПІСЛЯ цього фіксу.

### 2026-09-26: одноразовий виняток з rule 6 — видалено news/-дані, зібрані до фіксів якості
**Рішення користувача (явно, після того як я підняв конфлікт з rule
6):** `TRUNCATE raw_news, news_analysis, llm_call_log` — повне
очищення. Причина, названа користувачем: ці дані зібрані/проаналізовані

вони не "валідна історія, що застаріла", а результат ЗАВІДОМО

дані (macro observations тощо) від видалення через "джерело
змінилось/зникло" — тут інша ситуація: сам МЕТОД збору/аналізу був
дефектний, не джерело. Це одноразовий виняток для конкретного
випадку, не нова стандартна практика — news/, зібраний ПІСЛЯ цього
очищення (з фіксами), і далі підпадає під звичайне rule 6 (не
видаляти).
