### 2026-08-30: "Живий запит повернув 200 OK" ≠ "series key досі актуальний" — офіційні статдатасети іноді закриваються без помилки
**Рішення:** мало перевірити series key одним живим запитом перед
здачею користувачу (див. запис нижче, 2026-08-29). Додатково: якщо
отримане значення застаріле більш ніж на один звітний період — це
сигнал перевірити, чи датасет/dataflow не було замінено/закрито,
а не проблема з `lastNObservations`/логікою фільтрації.
**Чому:** `eurozone_hicp` через flowRef `ICP` (перевірений живим
запитом і з правильною структурою CSV) стабільно повертав 200 OK і
коректно розпарсені записи — але дані завмерли на грудні 2025.
Причина: ECB офіційно ЗАКРИВ датасет `ICP` 4 лютого 2026 (методологічна
реформа Eurostat — COICOP v2, нова база 2025=100, склад єврозони з
Болгарією) і замінив його новим датасетом `HICP` з іншим кодом
інституції-джерела (`4` → `4D0`) у ключі серії. Запит до старого
flowRef не повертав помилку — просто мовчки повертав історичні дані
без нових спостережень, бо серія технічно існує, просто більше не
оновлюється. Виправлено: `eurozone_hicp` тепер `HICP.M.U2.N.000000.4D0.ANR`.
**Наслідок для процесу:** "перевірено живим запитом" (попередній
запис) страхує від помилки в ключі на момент перевірки, але не від
майбутнього/недавнього закриття датасету джерелом. Для показників,
де в нормалізованих записах observed_at суттєво відстає від очікуваної
дати останнього релізу (звірити із загальновідомим графіком публікацій
або пошуком), варто одразу підозрювати заміну датасету, а не
дебажити код адаптера.

### 2026-08-29: Новий адаптер = новий рядок у sources + перевірка кожного series key живим запитом
**Рішення:** при додаванні адаптера для нового джерела (не нового
metric_id у вже існуючому джерелі) обов'язково: 1) додати рядок у
seed `INSERT INTO sources` у db/schema.sql; 2) перевірити КОЖЕН
series key/series id живим запитом (web_fetch або аналог) до того,
як віддавати на live-тест користувачу — не покладатись на непрямі
джерела (R-пакети, статті, старі API-довідники) без верифікації, що
структура серій не застаріла.
**Чому:** обидва пункти виявились реальними, а не гіпотетичними
ризиками при додаванні ecb_adapter.py (Фаза 1, сесія 4). (1) Юніт-тести
на фікстурах не торкаються БД і тому не ловлять відсутність джерела в
`sources` — перший live insert падав з `ForeignKeyViolation`, і
з'ясувалось це аж на машині користувача. (2) Series key для
`eurozone_unemployment_rate`, підібраний за старим датасетом `STS`,
повертав 404 — датасет був перейменований/перенесений у `LFSI` без
явного попередження в непрямих джерелах, звідки бралась структура
ключа.
**Відкинута альтернатива:** довіряти юніт-тестам на фікстурах як
достатньому доказу готовності до live-тесту — відкинуто, бо вони за
конструкцією (навмисно, щоб не залежати від мережі/БД у тестах)
перевіряють тільки логіку normalize(), а не існування джерела в БД чи
актуальність зовнішнього API.

### 2026-08-29: raw_observations зберігає тільки сирі значення, не % зміни
**Рішення:** data-ingestion/ ніколи не рахує й не зберігає похідні
величини (MoM/YoY % зміна, тренди, порівняння факт/консенсус) —
тільки сире значення показника, яке віддає джерело. Розрахунки
живуть у analysis/ і рахуються з сирих значень на льоту або в
окремих похідних таблицях (деталі — коли дійдемо до Фази 2).
**Чому:** з сирого індексу (напр. CPI = 314.121) можна порахувати
будь-яку зміну (MoM, YoY, QoQ, зміна від попередньої ревізії) — не
треба наперед вирішувати, яка саме знадобиться. Якщо зберігати
одразу готовий %, втрачаємо гнучкість і, що важливіше, ламаємо
коректну обробку ревізій (коли джерело переглядає минуле значення
заднім числом — % зміна "з коробки" стає неоднозначною: від якої
версії минулого значення її рахували?).
**Відкинута альтернатива:** тягнути з FRED вже готові % через
параметр `units=pch/pc1` як окремі metric_id. Відкинуто на цьому
етапі — дублює дані, прив'язує нас до методології розрахунку FRED
замість власної, і суперечить принципу "джерело даних не інтерпретує".
Можна повернутись до цього як до додаткової звірки в Фазі 2.
Повний список показників для Фази 1+ — docs/metrics-catalog.md.

### 2026-08-27: Стек — Python + PostgreSQL/TimescaleDB
**Рішення:** Python як мова бекенду; PostgreSQL з розширенням
TimescaleDB як єдина база даних (замість окремих time-series + реляційної

**Чому:** один інструмент для обох типів даних (ціни/показники як
часові ряди, метадані/звіти як реляційні дані) — менше операційної
складності, ніж підтримка двох окремих СУБД. Обидва компоненти
безкоштовні й з відкритим кодом.

### 2026-08-27: Джерела даних — пріоритет безкоштовних першоджерел
**Рішення:** повний список у data-ingestion/CLAUDE.md. Ключові вибори:
FRED/ECB SDW для макро, SEC EDGAR для звітів компаній, yfinance для

**Чому:** максимальне покриття безкоштовно, з пріоритетом на офіційні

Там, де офіційного безкоштовного API немає (ціни акцій/форекс/товарів
у реальному часі) — свідомо йдемо на компроміс через yfinance, з

**Відкинуті альтернативи:** Alpha Vantage як основне джерело цін
акцій — відкинуто через занадто обмежений безкоштовний рівень (25
запитів/день), непридатний навіть для помірного покриття ринку.

### 2026-08-27: Календар релізів з рівнем впливу — власна розмітка
**Рішення:** дати релізів беремо з офіційних графіків публікацій
(BLS/BEA/Fed/ECB), а рівень впливу (High/Medium/Low) підтримуємо як
власний статичний список типів релізів, а не з зовнішнього API.
**Чому:** офіційного безкоштовного API з готовою розміткою впливу не
існує — найпоширеніші джерела такої розмітки (напр. ForexFactory)
неофіційні. Розмітка "що є high-impact" — загальновідома і рідко
змінюється (NFP, CPI, FOMC, GDP, PCE), тому підтримувати її вручну —
прийнятний компроміс.

### 2026-08-29: Виправлення — partition column для hypertable — observed_at, не fetched_at
**Рішення:** raw_observations партиціонується (TimescaleDB hypertable) по
`observed_at`, а не по `fetched_at`, як було зроблено спочатку.
**Чому:** перша спроба (partition по fetched_at) впала з реальною помилкою
під час запуску: `create_hypertable()` вимагає, щоб УСІ unique-обмеження
таблиці (не тільки PRIMARY KEY) включали колонку партиціювання. Наш
`UNIQUE (source, metric_id, observed_at, revision)` не містив fetched_at,
і hypertable не створювався — весь init-скрипт після цього кроку
переривався, включно з `INSERT INTO sources`, що спричиняло
ForeignKeyViolation при першому запуску run_collect.py. observed_at і
так частина цього UNIQUE-обмеження, тож партиціювання по ньому
розв'язує проблему без штучного розширення ключа. Додатковий бонус:
типові запити analysis/ читають "дані за період X" (observed_at), не
"коли ми дізнались" (fetched_at) — тож це й ефективніше.
**Наслідок для існуючих локальних БД:** якщо volume вже піднімався зі
старою схемою (і впав на цьому кроці), треба `docker compose down -v`
і підняти заново — таблиця не встигла отримати жодних валідних даних
(усі insert'и падали на FK через незаповнену sources), тож втрати
історії немає.

### 2026-08-29: Revision обчислює шар збереження, не адаптер
**Рішення:** адаптери (напр. FredAdapter) завжди повертають
NormalizedRecord з `revision=None`. Фактичний номер ревізії визначає
`common/db.py:decide_revision()` під час запису — порівнянням нового
значення з останнім уже збереженим для того самого
(source, metric_id, observed_at).
**Чому:** data-ingestion/CLAUDE.md вимагає, щоб адаптер повертав
`revision` як частину нормалізованого запису, але визначити ревізію
можна лише знаючи історію — а адаптер за архітектурою (docs/architecture.md)
не повинен звертатись до сховища. Винесення рішення "яка це ревізія"
в окрему чисту функцію (без SQL) дозволяє покрити логіку тестами без
реальної БД і лишає адаптер простим: він не знає нічого, крім самого зовнішнього API.
**Відкинуті альтернативи:** давати адаптеру доступ до БД для
самостійного визначення ревізії — відкинуто, бо порушує розділення
"адаптер тільки збирає" і ускладнює тестування адаптерів (довелось би
мокати БД в кожному тесті адаптера, а не лише в тестах db.py).

**Рішення:** для e-Stat CPI Японії використовувати `statsDataId

### 2026-08-30: e-Stat — коди area/cat01 резолвляться в рантаймі, не хардкодяться
**Рішення:** `macro/estat_adapter.py` робить два мережеві виклики на
кожен `collect()`: (1) невеликий запит із `metaGetFlg=Y&limit=1`,
щоб отримати `CLASS_INF` і знайти код area, чия назва — "全国"
(національний), і код cat01, чия назва — "総合" (усі товари); (2)
основний запит уже з `cdArea`/`cdCat01`, знайденими на кроці 1.
**Чому:** на відміну від FRED (один string ID) і ECB/BOJ (пара
ідентифікаторів, задокументована для потрібного ряду наперед), у
e-Stat потрібний зріз визначається кодами класифікації, які
публікуються тільки як додаток-таблиця до кожної статистичної
таблиці окремо (не в єдиному довіднику), і мережа пісочниці Claude
не мала доступу до e-stat.go.jp, щоб дістати ці коди заздалегідь.
Резолюція за людинозрозумілою назвою ("全国"/"総合") замість
хардкоду коду — стійкіша до того, що коди можуть відрізнятись між
`statsDataId` (напр. між 2020- і 2025-базовими таблицями).
**Відкрите питання:** сам живий виклик до e-stat.go.jp ще не
підтверджено (ключ ESTAT_APP_ID додано користувачем, але мережевий
запит з пісочниці Claude недоступний) — перший `collect_all.py`/
`run_collect.py --metric japan_cpi` через Docker або підтвердить
підхід, або поверне зрозумілу помилку від `_resolve_area_and_cat01`
(явно каже, який код не знайдено), яку можна буде виправити
адресно, без здогадок наосліп.

### 2026-09-13: japan_cpi — знайдено і виправлено реальний баг з виміром `tab`
**Що сталось:** хоча `japan_cpi` формально пройшов live-прогін,
логи показали "фальшиві ревізії" в межах одного запуску — та сама
дата отримувала кілька різних значень підряд (напр. `101.5 → 0.5 →
1.5`). Причина: `_resolve_area_and_cat01()` (стара назва методу)
резолвила тільки виміри `area`/`cat01`, ігноруючи `tab` — а ця
таблиця CPI публікує кілька рядків на кожен місяць під різними
кодами `tab`: сам рівень індексу (`指数`, ~101) окремо від %-зміни
р/р (`前年同月比`) і %-зміни м/м (`前月比`). Без фільтрації за `tab`
усі три потрапляли в один `metric_id=japan_cpi` і перезаписували
одне одного в `raw_observations` як послідовні "ревізії" одного й
того самого числа — хоча насправді це три різні величини.
**Виправлено:** `_resolve_area_and_cat01()` → `_resolve_dimensions()`
— тепер резолвить УСІ виміри таблиці (крім `time`), а не тільки два
захардкоджені. Для виміру з рівно одним значенням неоднозначності
нема — береться автоматично. Для виміру з кількома значеннями
потрібен запис у новому словнику `_DIMENSION_PREFERENCES` (людино-
зрозуміла назва потрібного варіанту); якщо для такого виміру запису
нема — явний `ValueError` з переліком доступних назв замість
мовчазного змішування даних. Додано `_DIMENSION_PREFERENCES["tab"]
= "指数"`.
**Другий шар захисту:** `normalize()` тепер дедуплікує по
`observed_at` — якщо для однієї дати після фільтрації запиту все ж
трапляються різні значення (напр. з'явиться новий tab-код, для якого
забудуть додати пріоритет), залишається перше значення, конфлікт
логується `WARNING`, а не мовчки пишеться в БД як черговий запис.
**Чому не було виявлено раніше:** фікстура `estat_meta_response.json`
була написана заздалегідь (мережа пісочниці Claude не мала доступу
до e-stat.go.jp) без виміру `tab` взагалі — хоча фікстура даних уже
містила `@tab: "01"` в кожному записі, ніхто (жоден тест) не
перевіряв, що буває, коли `tab` має більше одного значення. Додано
тести саме на цей сценарій (`test_resolve_dimensions_picks_preferred_values`,
`test_normalize_deduplicates_conflicting_values_for_same_date`) і нову
фікстуру `estat_cpi_response_mixed_tab.json`.
**Відкрите питання:** сам факт того, що live-прогін "пройшов успішно"
попри зіпсовані дані, показує загальний ризик — `run_collect.py`/
`collect_all.py` вважають запис успішним, якщо `store()` не кинув
винятку, навіть якщо кілька підряд "revision" для однієї дати в
одному прогоні — явна ознака проблеми з джерелом/адаптером, а не
легітимна ревізія від статистичного бюро. Варто розглянути (не
зроблено зараз): попередження на рівні `collect_all.py`, якщо
кількість нових revision для одного metric_id в одному прогоні
перевищує якийсь поріг (напр. >1 на дату).

## Приклад запису (видалити, коли з'явиться перше реальне рішення)
### 2026-08-24: Формат сховища сирих даних
**Рішення:** append-only таблиці, без update/delete для фактичних даних.
**Чому:** потрібна можливість порівнювати "що знали тоді" з реальністю
пізніше; видалення/перезапис ламає цю можливість назавжди.
**Відкинуті альтернативи:** тримати тільки останнє значення кожного
показника (простіше, але втрачає історію ревізій даних, яка сама по собі
є сигналом).
