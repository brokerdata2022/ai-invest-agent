# Архітектура

## Потік даних (високий рівень)

```
[Зовнішні джерела]           [data-ingestion]        [сховище]
 - макро API                     адаптери         →   сирі дані
 - фінансові API          →      (по одному             (незмінні,
 - новинні стрічки                на джерело)            з timestamp)
 - звіти компаній

                                       ↓
                              [monitoring]
                        відстежує календар релізів,
                        детектує "щойно з'явились нові дані"
                                       ↓
                              [analysis]
                    - порівняння факт vs очікування
                    - оновлення прогнозів
                    - LLM-інтерпретація новин/звітів
                                       ↓
                              [reporting]
                    - короткий звіт
                    - список цікавих активів
                                       ↓
                              [користувач]
```

## Чому саме такий поділ на шари

Кожен шар має одну відповідальність і не знає про внутрішню логіку інших:

- **data-ingestion** не знає, ЩО буде зроблено з даними — лише збирає й
  нормалізує. Це дозволяє додавати нові джерела, не торкаючись аналізу.
- **monitoring** не аналізує самі дані — лише відстежує "коли щось нове
  з'явилось" і сигналізує analysis. Розділення важливе, бо логіка
  розкладу/тригерів (коли саме перевіряти) зовсім інша за природою, ніж
  логіка інтерпретації даних.
- **analysis** — єдине місце, де є "розумна" логіка (прогнози,
  інтерпретація). Якщо тут щось піде не так, це не зачіпає збір даних —
  можна перерахувати аналіз заново на вже зібраних даних.
- **reporting** — тільки представлення вже готового аналізу. Не повинен
  містити жодної аналітичної логіки — лише форматування.

Це дозволяє AI-агенту (Claude) працювати над кожним шаром окремо, без
ризику, що зміна в звітності випадково зламає збір даних чи навпаки.

## Чому сирі дані ніколи не видаляються

Прогнозна якість агента з часом залежить від можливості порівняти:
"що ми знали тоді" vs "що виявилось насправді". Якщо сирі історичні дані
видаляти чи перезаписувати, ця можливість втрачається назавжди. Тому
data-ingestion пише тільки додавання (append-only), ніколи update/delete
для вже збережених фактичних даних.

## Відкриті питання (навмисно не вирішені зараз)
- Джерело "ринкових очікувань" (консенсус-прогнози vs власна модель) —
  вимагає окремого дослідження перед Фазою 2
- Масштаб LLM-виклику: чи аналізувати кожну новину окремо, чи батчами
- Формат видачі фінального звіту користувачу

Рішення по кожному з цих пунктів записувати в decisions.md з датою й
коротким обґрунтуванням, коли будуть прийняті.
