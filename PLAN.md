Мета: скелет, що вміє надійно зберігати дані. Без цього аналіз будувати нема
на чому.

- [x] Обрати стек (мова, БД, оркестрація) — зафіксувати в CLAUDE.md
- [x] Базова схема БД: сирі дані, метадані джерел, лог релізів
      (db/schema.sql: raw_observations, sources, release_log)
- [x] Один-єдиний адаптер джерела даних (FRED, CPI/fed_funds_rate/
      unemployment_rate) — наскрізно, від збору (fetch) до нормалізації
      (normalize) і збереження (common/db.py)
- [x] Налаштування Telegram (reporting/telegram_notify.py, потребує
      TELEGRAM_BOT_TOKEN/TELEGRAM_CHAT_ID в .env)
- [x] Мінімальний тест: дані зібрались → лежать у БД → їх можна дістати

      Живий наскрізний прогін (run_collect.py → реальна TimescaleDB →
      telegram_notify.py) виконано і підтверджено локально 2026-08-29.

**Критерій завершення фази:** можна руками запустити збір одного показника
і побачити результат у БД. Нічого розумного ще не робимо.

## Фаза 1 — Збір даних (ширина, не глибина)
- [x] Макро-дані: 3-5 ключових показників (інфляція, ставки, безробіття, ввп —
      залежно від ринків, які цікавлять) — CPI, Core CPI, PCE Price Index,
      Fed Funds Rate, 10Y/2Y Treasury Yield, Unemployment Rate, Non-Farm
      Payrolls, Initial Jobless Claims, Real GDP, Retail Sales (усі через
      macro/fred_adapter.py:METRICS)
- [ ] Дані компаній: звіти (earnings), базові фінансові метрики
- [ ] Новини: підключення джерела + фільтрація за релевантністю
- [ ] Календар релізів (коли виходять наступні дані) — це критично для
      Фази 3 (моніторинг)
- [ ] Нормалізація: усі джерела приводяться до єдиного внутрішнього формату

**Критерій завершення фази:** дані з кількох різних джерел стабільно
збираються за розкладом без ручного втручання.

## Фаза 2 — Аналіз і прогнози

- [ ] Порівняння факту з очікуванням при виході нових даних

**Критерій завершення фази:** для одного показника агент може сказати
"вийшло X, очікувалось Y, це означає Z" одразу після релізу.
